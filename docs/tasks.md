# Tasks — standalone action items, triggerable from journeys (design record)

**Status: underlying domain retained; standalone platform UI hidden (September 2026).** Requests
and Reviews now cover the visible staff work queues. The task engine, API, permissions and journey
integration remain because journeys still raise and complete follow-up work, but the platform
sidebar, Spotlight, dashboard, client record and message rails no longer expose Tasks as a
standalone feature. The `/tasks` implementation is intentionally retained rather than deleted so
the domain can be revisited without undoing journey behaviour.

All four implementation phases were completed. Phase 1 (foundation): migration `0027_tasks`, the `role_ids`
claim, `tasks:read`/`tasks:write`, `app/tasks/service.py`, the `/tasks` router and the
RLS/behaviour tests (`tests/test_tasks_api.py`). Phase 2 (pipeline): per-step `tasks` specs
validated in `app/flows/definitions.py` + publish preflight, `task.requested` emission from
`orchestrator.apply_step_event`, and the outbox dispatcher (`app/flows/dispatcher.py`) hosted in
the background worker (`app/worker.py`), with `tests/test_tasks_pipeline.py`. Phase 3 (surfaces):
the platform Tasks inbox (`/tasks`, nav gated `tasks:read`; create dialog assigns by role slug /
staff user / client), tasks panels on journey detail + the client record's overview rail, client
action items on the client-portal home (`GET /tasks/me` + inline complete), and the flow editor's
"Raise a task" step-inspector section with a per-node ⚡ badge. Phase 4 (polish): migration
`0028_tasks_polish` — assign-time + near-due email notices via a worker-side scanner
(`app/tasks/notifier.py`, stamps `notified_at`/`due_soon_notified_at`, only runs when Resend is
configured), staff RLS re-scoped to the adviser's book (mirrors `0021_documents_scope`:
`contacts:read_all` sees all; book-scoped staff see staff/role work + own-book client tasks),
and the activity trail (`GET /tasks/{uid}/activity` off the audit spine + the platform
`/tasks/{uid}` detail page), with `tests/test_tasks_polish.py`. Remaining ideas (recurring
tasks, webhooks) live under open questions. This document remains the plan of record for the
`tasks` domain.

A **task** is a first-class, tenant-scoped action item: a thing somebody must do, with an
assignee, an optional subject, an optional due date, and an `open → done/cancelled` lifecycle.
Tasks stand alone — they are **not** flow steps, **not** document requests, and **not** four-eye
reviews ([`docs/reviews.md`](reviews.md); completing a task must never apply a bank-detail change)
— but they can be
**raised automatically by journey components** (a flow step completing, failing, or blocking),
by document events, or manually by staff. The design goal is one primitive that serves three
use cases equally: journey-driven follow-ups ("AML failed → raise a compliance review task"),
staff-to-staff work tracking, and client action items fulfilled in the client portal.

## History (why this is greenfield, not a revival)

`documents.document_tasks` was fully designed (`docs/proposed-schema.sql` ~L1123,
`docs/document-management.md` §tasks) but **never migrated or implemented** — it was consciously
superseded by the `requests`/`request_items` model before any code shipped
(`docs/openapi-outline.md` §tasks-consolidation). The only artefacts ever built were two
demo-fixture UIs (a platform assign-task dialog, a client `/tasks/[id]` route), both deleted on
the document-UI branch. Decisions worth carrying forward from that design:

- `tenant_id` **denormalised** onto the task row so RLS never subqueries a parent table.
- Client linkage is `contact_id → crm.contacts` (the client entity), never `auth.users` (a login).
- **"Action needed" is derived** from the existence of open tasks — never a stored status flag on
  the subject (avoids the cancel-stranding bug the old design documented).
- Completion carries `completed_by`/`completed_at`/`completion_data jsonb`.

What's new versus that design: tasks live in their **own schema** (not under `documents`), the
assignee is **polymorphic** (staff user / staff role / client contact, not client-only), and
creation is **event-driven** off the flow engine's transactional outbox.

## Data model (`tasks` schema — migration `0027_tasks`)

One table. `0027_tasks.sql` + `versions/0027_tasks.py`, `down_revision =
"0022_documents_activity_scope"` (the current head — note the migration _filename_ sequence and
the revision chain diverge after `0026`; the chain is authoritative).

```sql
CREATE SCHEMA tasks;

CREATE TABLE tasks.tasks (
  id          int PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  uid         text NOT NULL UNIQUE,                    -- 'tsk_...'
  tenant_id   int NOT NULL REFERENCES auth.tenants(id) ON DELETE CASCADE,

  -- What the task is about (optional): mirrors flows.cases' polymorphic subject.
  subject_type text CHECK (subject_type IN ('contact', 'account', 'execution', 'document')),
  subject_id   text,            -- id/uid in the subject's own namespace; NULL pair = ad-hoc
  CONSTRAINT tasks_subject_pair CHECK ((subject_type IS NULL) = (subject_id IS NULL)),

  -- What raised it (provenance + idempotency handle).
  source_kind text NOT NULL DEFAULT 'manual'
              CHECK (source_kind IN ('manual', 'flow', 'document', 'system')),
  source_ref  text,             -- e.g. 'fex_abc:step_kyc:contact_7:failed' for flow-raised

  -- Who must act: discriminated by assignee_kind. The CHECK forbids cross-kind contamination
  -- but allows the MATCHING column to go NULL: the user/role FKs are ON DELETE SET NULL, so a
  -- deleted role orphans its tasks (visible in "All", absent from "Mine") rather than blocking
  -- the delete or cascading work away. Creation-time NOT NULL is enforced by the service layer.
  assignee_kind        text NOT NULL CHECK (assignee_kind IN ('user', 'role', 'contact')),
  assignee_user_id     uuid REFERENCES auth.users(id)    ON DELETE SET NULL,
  assignee_role_id     int  REFERENCES auth.roles(id)    ON DELETE SET NULL,
  assignee_contact_id  int  REFERENCES crm.contacts(id)  ON DELETE CASCADE,
  CONSTRAINT tasks_one_assignee CHECK (
    (assignee_kind = 'user'    AND assignee_role_id IS NULL AND assignee_contact_id IS NULL) OR
    (assignee_kind = 'role'    AND assignee_user_id IS NULL AND assignee_contact_id IS NULL) OR
    (assignee_kind = 'contact' AND assignee_user_id IS NULL AND assignee_role_id  IS NULL)),

  category    text NOT NULL DEFAULT 'generic'
              CHECK (category IN ('review', 'acknowledge', 'upload', 'follow_up', 'generic')),
  title       text NOT NULL,
  description text,
  due_date    date,
  priority    text NOT NULL DEFAULT 'normal' CHECK (priority IN ('low', 'normal', 'high')),

  status      text NOT NULL DEFAULT 'open'
              CHECK (status IN ('open', 'in_progress', 'done', 'cancelled')),

  created_by      uuid REFERENCES auth.users(id),        -- NULL = system/flow-raised
  completed_by    uuid REFERENCES auth.users(id),
  completed_at    timestamptz,
  completion_data jsonb,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX tasks_tenant_status_idx   ON tasks.tasks (tenant_id, status);
CREATE INDEX tasks_assignee_user_idx   ON tasks.tasks (assignee_user_id)    WHERE assignee_user_id IS NOT NULL;
CREATE INDEX tasks_assignee_role_idx   ON tasks.tasks (assignee_role_id)    WHERE assignee_role_id IS NOT NULL;
CREATE INDEX tasks_assignee_contact_idx ON tasks.tasks (assignee_contact_id) WHERE assignee_contact_id IS NOT NULL;
CREATE INDEX tasks_subject_idx         ON tasks.tasks (subject_type, subject_id) WHERE subject_type IS NOT NULL;

-- Idempotency: an automated source may only ever raise one task per source_ref. Retried outbox
-- deliveries and re-fired handlers collapse here, so the pipeline needs no dedupe of its own.
CREATE UNIQUE INDEX tasks_source_ref_key ON tasks.tasks (tenant_id, source_kind, source_ref)
  WHERE source_kind <> 'manual' AND source_ref IS NOT NULL;
```

Notes:

- `subject_id` is `text` (not a polymorphic int) because subjects span namespaces — `crm.contacts`
  ints, `flows.executions` uids, `documents.documents` uuids. The service layer validates the
  pair; there is deliberately no FK (same trade-off as `flows.cases.resource_type/resource_id`).
- **No `task_type` execution semantics.** The old design's `task_type` conflated "what kind of
  work" with "how it's fulfilled". Here `category` is a label only; fulfilment is always
  "a human marks it done" (optionally attaching `completion_data`). Anything needing structured
  fulfilment (a form, an upload, a signature) should be a document **request** — tasks link to
  one via `subject_type='document'` or the description, they don't reimplement it.

### RLS

Enable + FORCE RLS. Policies (staff read/write mirrors the documents pattern; the assignee
branch makes tasks visible to whoever must act):

```sql
-- Read: staff within tenant lineage; a client sees tasks assigned to their contact scope;
-- a staff user additionally sees tasks assigned to them or to a role they hold.
CREATE POLICY tasks_read ON tasks.tasks FOR SELECT TO authenticated USING (
  tenant_id = ANY (auth.tenant_lineage())
  OR assignee_contact_id = ANY (auth.contact_scope())
);
-- Write: staff within lineage; a client may update (complete) only a task assigned to them.
CREATE POLICY tasks_write ON tasks.tasks FOR ALL TO authenticated
  USING     (tenant_id = ANY (auth.tenant_lineage()) OR assignee_contact_id = ANY (auth.contact_scope()))
  WITH CHECK (tenant_id = ANY (auth.tenant_lineage()) OR assignee_contact_id = ANY (auth.contact_scope()));
GRANT SELECT, INSERT, UPDATE ON tasks.tasks TO authenticated;  -- no DELETE: cancel, don't erase
GRANT ALL ON tasks.tasks TO service_role;                       -- the dispatcher writes elevated
```

**Role-visibility claim.** "My tasks" filtering for role-assigned tasks needs to know which roles
the caller holds. Policies must do **zero `auth.*` queries per row** (the 0001 invariant), so
`auth.resolve_claims` is extended (CREATE OR REPLACE in `0027`) to mint a `role_ids` claim —
`int[]` of the caller's `organisation_memberships.role_id` for the resolved tenant (one per
portal today; array-shaped for safety) — plus an `auth.role_ids()` helper mirroring
`auth.contact_scope()` (fail-closed to `'{}'`). Tenant-wide staff can _see_ all tenant tasks
regardless (the lineage branch); `role_ids` drives the **"mine" inbox filter** and any future
book-scoping tightening, it does not gate visibility in v1.

### Permissions

`app/permissions.py` registry, consistent read/write pair (auto-synced on startup):

- `tasks:read` — view the firm's tasks (platform portal).
- `tasks:write` — create, reassign, complete, cancel tasks (implies read).

Client-portal access needs **no permission**: like `GET /applications/me`, the client surface
only ever returns rows RLS already scopes to the caller's own contacts.

## Service layer (`app/tasks/service.py`)

One synchronous primitive every producer calls — the API router, the outbox dispatcher, document
routers, future CRM hooks:

```
async def create_task(session, *, tenant_id, assignee, title, category='generic',
                      subject=None, source=('manual', None), description=None,
                      due_date=None, priority='normal', created_by=None) -> TaskOut
```

It validates the assignee exists **in this tenant** (a role's `tenant_id` must match; a contact
must belong to the tenant; a user must hold a membership), validates the subject pair, generates
the uid, inserts, and appends a `tasks.task.created` audit event (`audit.log`, the 0001 spine).
`ON CONFLICT` on `tasks_source_ref_key` → returns the existing row (idempotent creation).
Companion helpers: `complete_task`, `cancel_task`, `reassign_task`, each auditing.

## Event-driven creation (the journey trigger)

The flow engine already has the right seam and it is **unclaimed**: `flows.domain_events` is the
append-only fact log written on every step transition (`orchestrator.apply_step_event`), and
`flows.outbox` is a fully-built transactional delivery queue (claim via `FOR UPDATE SKIP LOCKED`,
exponential backoff, dead-letter — `app/flows/notifications.py`) with **no producer and no
running consumer**. Tasks become its first real tenant:

1. **Emission.** When a step transition lands, the orchestrator checks the step definition for
   task specs matching the signal (see authoring below) and, in the **same transaction** as the
   status write + domain event, `enqueue`s a `task.requested` outbox row:
   `payload = {spec..., execution_uid, step_key, participant_subject_id, signal}` with a
   deterministic `source_ref` (`{exec_uid}:{step_key}[:{participant}]:{signal}`).
2. **Dispatch.** A generic outbox dispatcher drains due rows and routes **by `event_type`**:
   `task.requested` → `tasks.service.create_task` (service_role session); `notify.*` → the
   existing email path (`deliver_due`'s send). Unknown types dead-letter with a clear error.
   Routing lives in a small handler table so later event types (webhooks, CRM sync) bolt on.
3. **Host process.** The dispatcher loop joins the existing background worker process
   (`app/worker.py` `run_forever`, 2s poll) as a second drain alongside `render_jobs` — one
   deployment unit, not two. If task/notification volume ever justifies isolation, it splits out
   with no schema change (the queue is the contract). _(Decision: piggyback now, split later.)_
4. **Idempotency.** Delivery is at-least-once by design; duplicates collapse at
   `tasks_source_ref_key` (the service's `ON CONFLICT` path), **not** in the pipeline. The known
   wart that `domain_events.idempotency_key` gets a fresh uid per call (never dedupes) is left
   alone — the fact log's semantics don't affect task correctness and fixing it is orthogonal.

Direct producers (manual creation via the router, document events) call `create_task`
synchronously — the outbox hop exists only where the producer is the engine mid-transaction.

## Journey authoring (flow-definition surface)

A step definition gains an optional `tasks` key — validated in `app/flows/definitions.py`
(strict allowlist, like `intake`):

```jsonc
{
  "id": "aml", "type": "kyc_aml", ...,
  "tasks": [
    { "on": "failed",                       // completed | failed | blocked | waiting
      "assign_to": {"kind": "role", "role": "compliance"},   // or {"kind": "user", "user_id"} |
                                                             //    {"kind": "participant"}
      "category": "review",
      "title": "AML review — {participant_name}",
      "due_days": 3, "priority": "high" }
  ]
}
```

- `on` maps 1:1 to the four `StepSignal`s — so "raise a task off a decision branch" needs no new
  engine concept: decision branches in the editor are projections of step conditions/signals, and
  the failure branch of a check _is_ `on: "failed"`.
- `assign_to.role` is a role **slug**, resolved to the tenant's `auth.roles` row at **dispatch**
  time, not emission (definitions are copied between tenants; ids don't travel, slugs do — and a
  step transition must never fail because a task spec is broken: a bad slug dead-letters the
  outbox row with the reason instead). Publish preflight (`_reference_issues`) fails a version
  whose specs point at roles/users the firm doesn't have. `{"kind": "participant"}` assigns to
  the step's participant contact — the "client action item" case.
- A journey can name who its platform-side work belongs to (`flows.executions.assignee_user_id`,
  any active platform member of the firm, not only an adviser). When that person is set, a staff
  spec (`role` or `user`) is delivered to them instead of the authored assignee. A `participant`
  spec is never redirected. Changing the assignee moves the journey's open staff tasks; clearing
  it leaves those tasks where they are, and later staff tasks fall back to the authored assignee.
- `due_days` is an offset applied at dispatch; `title`/`description` support the placeholder set
  `{participant_name}`, `{flow_name}`, `{step_title}`.
- **Editor:** the step inspector gets a "Raise a task" section (add/remove specs: trigger, assignee
  picker, category, title, due offset, priority). On the canvas, a small corner badge on nodes
  that raise tasks — no new node type; specs are step properties, deliberately unlike the
  blocking `task` _step type_ (a step the flow waits on), which stays as-is.

## API (`app/routers/tasks.py`)

| Method | Path                    | Gate                               | Purpose                                                                                                                                                      |
| ------ | ----------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/tasks`                | `tasks:read`                       | List/filter: `status`, `assignee` (`me`/`role:{id}`/`user:{id}`/`contact:{id}`), `subject_type`+`subject_id`, `category`, `overdue`; keyset pagination       |
| POST   | `/tasks`                | `tasks:write`                      | Create (manual) — body mirrors `create_task`                                                                                                                 |
| GET    | `/tasks/{uid}`          | `tasks:read`                       | Detail                                                                                                                                                       |
| PATCH  | `/tasks/{uid}`          | `tasks:write`                      | Edit / reassign / status transitions (staff)                                                                                                                 |
| POST   | `/tasks/{uid}/complete` | client: RLS · staff: `tasks:write` | Complete; clients stay gate-free (RLS limits them to their own action items — the point of the surface); staff need `tasks:write`; accepts `completion_data` |
| GET    | `/tasks/me`             | _(none — RLS)_                     | The caller's action items (client portal; `firm_session`-style contact scoping)                                                                              |

All on `tenant_session`; regenerate the TS client + permissions after (`api-client:generate`,
`api:generate-permissions`).

## Portal surfaces

- **Platform — Tasks inbox** (`/tasks`): the primary staff surface, and it opens on the reader's
  OWN work. _Assigned to me_ / _Everyone_ is a SERVER filter (`GET /tasks?assignee=me` — the caller
  plus their `role_ids`) carried in the page's URL as `?assignee=all`, because the inbox pages: a
  slice of the window in hand answers "you have nothing" whenever none of the newest 50 happen to
  be yours, which is how a scoped view stops being trusted. `me` is the default and stays out of
  the URL, so a shared link means "your tasks" to whoever opens it.

  _Open_ / _Done_ is a SEPARATE control over the rows that arrived. The two were one three-armed
  tab (_Mine_ / _All_ / _Done_), so choosing Done silently discarded the scope and answered with
  everyone's completed work. The tab you are not on carries its own count and an empty inbox names
  what is sitting under it — "no tasks" over a scoped book is the sentence that makes a reader stop
  believing the filter. Plus: group by due date, badge overdue, create-task dialog (assignee picker:
  staff, role, or client). Nav item between Journeys and Documents.

  The ops mount (`/tenants/{uid}/operate/tasks`) passes no scope and so is offered no control: an
  operator reads a firm's book from outside it, where "assigned to me" can only ever be empty.

- **Platform — dashboard "Needs you"**: the same question, one screen earlier, answered now by
  the reader's own onboarding (`GET /applications?mine=true` — assigned to them, or unassigned
  and theirs as the adviser, compared against `auth.uid()` in the API) and the reviews awaiting
  them (`GET /reviews?scope=inbox`). A dot on the right marks a row whose next move is the
  reader's; under the list sit their own notes (`/me/notes`, `platform.staff_notes`). It used to
  be the reader's own tasks (`assignee=me`) and requests for clients on their book
  (`GET /documents/requests?adviser=me`); tasks left the platform UI with the rest of the
  standalone surface, and requests left the rail when the requests queue moved behind
  `documents:show`. The principle held throughout: a firm-wide list beside your own work is
  somebody else's, which is what trains an adviser to ignore it.
- **Platform — in-context panels**: a Tasks card on journey detail (`/journeys/[uid]`, tasks with
  `subject_type='execution'`) and on the client record (tasks for that contact — both as subject
  and as assignee).
- **Client — action items**: open `assignee_kind='contact'` tasks surface on the client home and
  a simple list; complete-with-note inline. Mirrors the onboarding checklist pattern
  (`/applications/me` → here `GET /tasks/me`).
- **Derived "action needed"**: any surface wanting a flag (a journey card, a contact row) counts
  open tasks against that subject — no flag column anywhere.

## Delivery phases

1. **Foundation** — `0027_tasks` (schema + RLS + `role_ids` claim), permission registry entries,
   `app/tasks/service.py`, `app/routers/tasks.py`, client regen. Tests: RLS matrix
   (staff/client/role visibility, cross-tenant), service validation, router behaviour.
2. **Pipeline** — outbox routing table + `task.requested` handler, dispatcher joined to the
   worker loop, orchestrator emission from step task specs, `definitions.py` validation +
   publish-time preflight. Tests: end-to-end "step fails → outbox → task exists", retry/dup
   collapse, dead-letter on bad spec.
3. **Surfaces** — platform inbox + dialog + panels; client action items; editor "Raise a task"
   inspector section + canvas badge.
4. **Polish (fast-follow)** — Resend notifications on assign/near-due (reusing the outbox
   `notify.*` path), book-scoped staff visibility (align with `0021_documents_scope`'s pattern),
   task activity trail on the detail view.

## Known constraints & open questions

- **v2 flag**: journey-triggered tasks fire only where `flows_orchestrator_v2` is enabled
  (the emission point is the v2 orchestrator). Manual/document/API tasks work regardless.
  Confirm the flag's rollout state before relying on phase 2 in production.
- **Cases' staff RLS is tenant-wide** (not book-scoped, unlike documents post-`0021`): tasks
  launch matching the cases behaviour, tightening to book scope in phase 4 alongside cases.
- **Recurring / scheduled tasks** (e.g. annual review): out of scope; the schema doesn't preclude
  a later `schedule` producer writing through the same service.
- **Notifications**: phase 4; assign-time email to a user/role is the first candidate once the
  `notify.*` path has a host (which phase 2 incidentally provides).
