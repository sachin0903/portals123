### CRM

This domain has genuinely moved, and it is the best-evidenced remediation I could find: 27 baseline functions, and the two headline blockers (a cash withdrawal validated against total account value; a created client invisible to its own creator) are properly fixed in the service layer, not the portal, and pinned by DB-backed tests I ran and passed (31 in tests/test_instructions.py, 14 in tests/test_crm_api.py, 89 in the platform clients vitest files). I attacked the withdrawal control on eight vectors — repetition, kind-swapping, cash-named equity funds, NaN/inf amounts, concurrency, archived/disabled clients, foreign models, direct API call bypassing the SvelteKit action — and every one was already anticipated and tested. Fabricated money is gone: the rescaled performance series and the rescaled holdings units are deleted rather than papered over, and every figure now carries a source and an as-at. What remains is real: nothing settles an instruction, there is no approval or bank-detail capture on a cash-out, `platform.accounts.value` is still a hand-run CLI snapshot with no refresh job, `POST /firm/contacts` still accepts an empty body and an unvalidated email (every email/name rule lives only in the SvelteKit action), and the provider lake still silently falls back to the committed 38 MB demo fixture — which the withdrawal control now depends on. No CRM function's status depends on migrations 0030–0035: archive uses `deleted_at` from 0002 and the adviser-book claim already unions `crm.client_advisers` in 0027, so needs_migration is false throughout.

### Documents

This domain has moved further than any self-report deserves credit for by default, and most of it holds up under tracing: the library's loadError now renders, an Archived view + `/unarchive` endpoint exist and are wired, multi-file uploads genuinely post every part and report per-file rejections, `document_type` is a single validated vocabulary with a server-side freeze on both write paths, Send persists the covering note and queues real email through the outbox dispatcher, the whole requests engine (create/list/detail/cancel/due-date/reassign) got a staff UI plus a standalone client inbox, and the two fake tabs (Tags, Versions) were deleted rather than papered over. The share throttle and provenance capture are the best-verified work here — the tests actively attack them (repeated/rotated X-Forwarded-For, dressed-up URLs, hashed keys). What has NOT moved: no server-side paging anywhere, no URL state on filters, request cancel/due-date still write no product event and there is still no overdue/reminder job, forms-response review is byte-for-byte unchanged, and file upload/download/delete remain unaudited. Two things read as fixed but are not reachable: the share-link email + covering message exist in the API with zero callers, and book-scoping of `documents.shares`/`documents.attachments` lives only in unapplied migration 0031 — so on the running deployment a book-scoped adviser can still list another book's share tokens and download any client's passport.

### Authoring

The remediation was real but extremely uneven in coverage: `render/resolve.py`, `datasets.py`, `documents.py` and `worker.py` were substantially rewritten and are backed by ~800 new tests that run against a real Postgres with migrations 0030–0035 applied — the tenant-SQL escalation, the silent-empty-dataset failure mode, dataset scope, the dead-letter/retry hole and the dataset preview are genuinely fixed, and I could not defeat the new SQL guard with ~70 attack payloads. But `apps/api/app/routers/templates.py`, `forms.py`, the whole template editor, the forms UI and `packages/ui` were not touched at all (`git diff 266c1a4..HEAD` over those paths is empty), so 20 of the 49 functions are byte-for-byte unchanged from the baseline. Two items are real only once the unapplied migration 0032 lands — and 0032 turns the published-version renderer PATCH from a silent data corruption into an unhandled 500, because `templates.py` was never taught to catch the new SQLSTATE.

### Journeys

This domain moved a long way and most of it is real: the FLOWS_ORCHESTRATOR_V2 outage, journey cancellation, generate_document, depends_on enforcement, flow archiving, dead-letter visibility, the staff fill_form surface and task reassign/edit are all genuinely wired end to end and covered by a green 1654-test suite that runs against a real Postgres 18 testcontainer (I confirmed the container actually starts). Nothing in this domain depends on the unapplied migrations 0030-0035 — they add no column or function this code reads. The un-remediated half is the authoring surface and the client portal: the flow editor still has no inspector branch for setup_account or upload_document, no milestones, no reordering and no version history; the visibility editor still stores every value as a string so the four boolean fields it offers can never match; and apps/client/src/routes/onboarding was not touched at all, so it still flattens every journey into one synthetic case, never snapshots the form, and now renders a dead "Complete" button plus an empty form dialog for the steps the new depends_on hold keeps pending.

### Admin

Real, substantial movement: the admin domain's two 💥 items, its 🎭 kill switch, its 🎭 SearchBar and its ❌ offboarding/roles-reconcile gaps are all genuinely closed, wired end to end from a user action, and covered by 78 passing API tests plus 91 passing admin-app unit tests. The remaining honest caveats are (a) three headline fixes live only in unapplied migrations — the model role preset (0033) and the `auth.role_permissions` audit attachment (0030) — so on a running deployment a cloned firm still gets zero roles and role-permission grants are still unaudited; and (b) two "fixed in a diff, inert in production" survivors: the branding `StorageUnavailable` 409 whose only trigger is a monkeypatch (the real code still base64-inlines logos into jsonb), and the platform portal's branding action which still omits `icon`. I also found one new privilege-boundary hole introduced by the remediation (the tenant export endpoint's gate ignores the target tenant) and one pre-existing hole the new kill switch does not cover (public document share links).

### Core

Very substantial and mostly real remediation: search went from three fabricated bars to a genuine RLS-scoped `/search` endpoint consumed by all three portals; change-password is now real on all three portals with a session sweep; the worker got a heartbeat healthcheck, dead-letter endpoint/replay/UI and a leader-elected poller; observability (structured JSON logs, correlation middleware, `/health/ready`, `/metrics`, a Sentry facade) was built from nothing; the deploy now builds before migrating, polls the Coolify outcome and smoke-tests readiness, and PR CI applies every migration to a real Postgres twice. The whole API suite (1654 tests) passes, and the new RLS suites (93 tests across `test_schema_invariants`/`test_rls_directory`/`test_rls_book_scope`/`test_rls_link_tenant`) are genuinely adversarial. Two things temper it: **the biggest RLS wins live only in unapplied migrations 0030–0035**, so on a running deployment `auth.tenants` still reads `USING (true)`, KYC/cases/shares are still tenant-wide, the model tenant is still blank and `auth.resolve_claims` is still an unguarded oracle; and **three "fixes" are inert or unreachable on the deployed stack** — the login rate limiter (`POST /internal/rate-limit` has zero callers), Sentry and `/metrics` (neither `SENTRY_DSN` nor `METRICS_TOKEN` is passed to the `api` service in `docker-compose.yaml`). The platform portal's ghost-nav 403 traps are untouched, and the client-portal home still falls back to fictional fixtures from `@graphene/ui`.
