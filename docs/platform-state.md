# Platform state — what is built, and the decisions behind it

The running account of what exists, why it is shaped the way it is, and what was
deliberately not done. It is deep by design: most paragraphs record a decision that was
reversed at least once, or a failure whose symptom named the wrong cause.

**This is a companion to the subject docs, not a replacement.** Each area has its own —
`auth.md`, `flows.md`, `aml.md`, `partner-api.md`, `comms.md`, `messaging.md`, `contributions.md`,
`platform-model.md`, `provider-pipeline.md`, `document-management.md`,
`portal-customisation.md` — and those are authoritative on their own subject. The
firm-facing partner API (Litestar, `apps/api/external`, schema `compliance`) is
[`docs/partner-api.md`](partner-api.md). What is here
is the cross-cutting narrative: how the pieces came to fit together, and which of them
supersede each other.

It lived in `CLAUDE.md` until it reached 229KB and was being loaded into every session in
full. Nothing was deleted in the move.

## Schema and migration history

**Head is `0150_model_charge_percent` (Sept 2026; `0146_orgs_are_nodes` is the last one with a story, below):** `0131_staff_profile` (what a FIRM says about its staff — job title, qualifications, FCA reference, bio, photo, direct line — plus `provider_refs`, WHICH ID EACH CUSTODIAN KNOWS THE PERSON BY, all as **columns on `auth.users`**. A `crm.users` table was written first and reverted, and the argument for it was FALSE: it held that `auth.users` is a WorkOS projection the sync overwrites, so a firm's own words would sit in a table whose contract is "the IdP is authoritative" — but every `UPDATE auth.users SET` in the estate names its columns, and `avatar` is already display data there. The second argument was real and is about a different table: `platform.links.entity_id` is `bigint` where `auth.users.id` is a `uuid`, so a login cannot be addressed by the provider-mapping table — answered by the provider's id being a COLUMN here, which is exactly what `workos_user_id` already is for the IdP. The table cost a second RLS policy, a backfill, a sync chokepoint, a tripwire test and three tables with "user" in the name. **A custodian's own people ARE rows now — `0123` reversed that, deliberately, and 0118's header records the three objections and how each is answered.** The reversal is `auth.merge_provider_user`: a custodian's employee user ATTACHES its id to the Graphene login already holding the same email, and otherwise INSERTS a disabled placeholder. (1) `UNIQUE (tenant_id, email)` was the decisive objection and is now the SIGNAL rather than an accident — what was rejected was an IMPLICIT merge with nobody confirming it, where this states the rule as DDL, requires an exact match and EXACTLY ONE of them (`aml.match_contact`'s bar, and two can match because the key is case-SENSITIVE), and SKIPS every ambiguous case rather than guessing (it files no reject ledger at all — each of the three reasons tried turned out to be answerable better elsewhere, and a skip loses nothing because `platform.users` and `provider_refs` are both readable, so what is unmapped is a comparison rather than a stored list that would go stale nightly). An operator's own mapping is never overwritten. (2) The read policy DOES gate on an `auth.organisation_memberships` row — and `auth_users_scoped_read` does not read its STATUS while `auth.resolve_claims` grants a portal only on `status = 'active'`, so an **`inactive`** membership makes the person readable to their own firm and grants nothing; inventing an ACTIVE one would still be wrong. (3) The volume figure was misleading: 1,591 is the whole report and **`USER_TYPE` splits it 706 Employee / 865 End Client / 20 Data Integration**, so only Employee is synced — publishing the End Clients would have put investors in a firm's STAFF list and let the attach rule bind a custodian's staff id onto a client's own portal login, and the adviser picker would offer a firm its own clients as advisers. That scope is corroborated rather than asserted: of the 233 distinct `ACCOUNT_DSR_EMP_ID` values in `ClientAccountLink`, the 37 that appear in `UserDetail` at all are **37 of 37 Employee**. 470 of the 706 are already departed (`USER_STATUS = 'N'`) and are still synced, because a departed adviser is the name on every account they advised. **`book_writer` still holds no privilege on `auth.users`** — the function is SECURITY DEFINER owned by `service_role`, so the pipeline executes those statements and cannot touch any other column of a login; the one consequence is that `merge.py` grants the staged TEMP view to `service_role`, or the definer cannot read its own input. The drop is the POPULATION and the API is the EMAIL (`UserDetail` is twelve columns with no address of any kind and one `USER_DISPLAY_NAME` holding "Armasoiu, Maria"), and **both of the vendor's scopes turned out to be OPTIONAL** with every row carrying its own `firmId` — so it is one paged sweep, not a request per firm per servicing relationship. With no API credentials the population still lands with every email NULL, which the merge counts as `no email at the provider` rather than inventing an address: `auth.users.email` is what a login is addressed by and what the send guard reads, so a plausible fabrication there is one careless invite from being treated as real. **The MANUAL half is built too**: the members **Edit drawer** carries a picker per enabled custodian for the people the email match declines to guess at, and `provisioning.set_provider_ref` is ONE implementation behind two routes (`PUT /users/{user_id}/provider-ref/{provider}` for the firm, `/admin/tenants/…` for operations — one act through two doors, which is why `test_collapsed_acts_are_declared_deliberately` now counts 28). **The picker reads the firm's own lake slice rather than calling the vendor, reversing what 0118 planned** (`app/lake/staff.py`): the pipeline already fetches that endpoint nightly, the lake copy is the CONFORMED one (scoped to the firm, filtered to employees — the live response carries no `userType` at all, so a picker fed from it would offer a firm its own clients as advisers), and SEI allowlists its API BY SOURCE IP so a live call works from the pipeline's host and not necessarily from the API's. It raises rather than returning `[]` when the chain has not run, because an empty dropdown that means "unreadable" looks exactly like one that means "this firm has no staff there". `pkgs/sei`'s `ReferenceApi.firm_employee_users` consequently has no in-app caller and stays as part of that client's faithful vendor surface. Both team surfaces TAG a person with the custodians that know them (`providers` + `from_provider` off `provider_refs`), named server-side by `providers.meta()` because six hard-coded copies had drifted and the one that mattered named the wrong custodian; the list orders a firm's own people first, since firm 3102 alone has 546 employee users. **The email also raises the floor on matching without changing the rule:** "never inferred" was written against display NAMES and stands — only 37 of the 233 distinct `ACCOUNT_DSR_EMP_ID` values in SEI's `ClientAccountLink` appear in `UserDetail` at all, so a name match would be wrong 84% of the time — but an email is an identity rather than a label, so an exact match on one, and exactly one (the bar `aml.match_contact` already sets for a person), is a defensible PROPOSAL for an operator to accept, and a miss is the common case rather than an error. That tripwire is not decoration: the identity model DELETED a `role='client'` belt for classifying people off a claim, and a `text[]` containing the word `client` is close enough to that mistake to forbid by test rather than by intention — and the failure would be silent, because for most people "is a client" and "holds the client portal" agree; the divergence is exactly the staff member who is also a client of their own firm, which is what an ARRAY is for. **`is_adviser` is a BOOLEAN and not a third `type` member (0125), because advising is a capability WITHIN staff rather than a peer of the other two**: as a member it made `{client, adviser}` expressible and there is no such person, where `users_adviser_is_staff` now makes that unrepresentable. ## State & next steps

Auth is built end-to-end (login, email verification, optional TOTP MFA, sealed-session cookies, JWT-verified API calls, logout) with **no self-service signup** — users are provisioned in WorkOS. The shared logic lives in `pkgs/auth` and is consumed by all three portals (`client`, `platform`, `admin`).

**WorkOS mirror reconciliation no longer runs inside uvicorn (Sept 2026).** The 60-second default remains enabled in staging and production, but `app.worker` owns the loop and reports it through the worker heartbeat. All WorkOS HTTP paths used by async API and worker code use `AsyncWorkOSClient`; slow Events, membership, invitation, role or security calls therefore yield instead of starving the API's single event loop. The existing per-environment transaction-scoped advisory lock still serialises cursor application across overlapping worker generations. This fixes the observed 30–60 second whole-site freezes where the in-container `/health` endpoint timed out while the database stayed at 20 ms.

The data model is now being landed forward (decision records: `docs/data-architecture.md`, `docs/identity-and-access.md`; reference: `docs/proposed-schema.sql`). **`0001_auth_core`** is in: the `auth`/`audit` schemas, the claim-driven RLS helpers + `auth.resolve_claims` minter, and the append-only audit spine. The request layer is wired to it — `db.py::tenant_session` sets `SET LOCAL ROLE authenticated` + `request.jwt.claims`, and `tests/test_rls.py` proves cross-tenant isolation against a real Postgres (testcontainers). **Identity model — project-per-tenant, APP-PER-PORTAL (rebuilt Aug 2026, `docs/auth.md` + `docs/auth-audit.md`).** White-label: each firm gets its own WorkOS **project**, so clients/staff of different firms never share a login. Both are re-checked at dispatch, not just at publish. **PII minimisation is the `input_fields` allowlist** (`lookup`'s `request_mapping` shape) — the ONLY thing sent, bounded by field count/per-value/total chars, refusing rather than trimming; sources are the closed condition scopes plus `memory.*`, and **`event.subject.*` is refused outright**. **The AML rail (do not weaken):** no AML/KYC/screening field may enter an input, a draft's context or memory — the field registry has no AML scope, `memory.*` is only safe because nothing writes a screening outcome into it (`on_aml_result` writes `crm.kyc_checks`; a test pins that), a name-shaped deny list runs at publish AND dispatch, and the draft prompt forbids describing any screening process. **The cost bound is real:** `flows.ai_usage` is append-only (no UPDATE/DELETE grant even for `service_role`), written on its OWN connection so a rolled-back action still meters the tokens it spent, and the per-tenant monthly token ceiling refuses with a reason an operator can see — checked-not-reserved, stated honestly. **It records the fact, never the content** — no prompt, no completion; the table has no column and `record()` no parameter, both pinned. `safety.aiTimeoutMs` is 10s **because of the worker, not the model**: 25 firings × 10s and 20 timer resumptions × 10s both fit the 300s stall allowances where 30s fits neither, so `MAX_DRAFT_TOKENS` is a covering note sized to the budget. **Prompt injection:** untrusted text is fenced in the user turn with the fence sequences stripped, never in the system prompt — but the real defence is the schema `enum` plus the fact that nothing downstream is an action; steering BETWEEN declared labels is not defended and the mitigation is authorial (never put a control on a classify output). Not built: a document-text source, streaming, retries (`max_retries=0`) or a fallback model (a provider refusal is an outcome, not something to shop around).

**Client<->adviser messaging is built end to end, including file attachments (`docs/messaging.md`) — explicitly a first-pass prototype, not the production design.** Schema `messaging`: one channel per client (`conversations`, `adviser_user_id` a mutable pointer re-synced from `crm.client_advisers`, no reassignment ledger yet — `audit.actions` already carries who/when for whatever writes that table), append-only `messages` (`body` now nullable — a message may be attachment-only), and append-only `attachments` (one row per FILE; `message_id` was `UNIQUE` until 0123). RLS is the same `tenant_lineage() OR contact_scope()` mix `crm.client_advisers` uses; the real identity gotcha this suite pins is that a client's WorkOS role is never literally `'client'` (`auth.portal() = 'client'` is the actual signal, `auth.role()` kept only as the same legacy fallback `auth.tenant_lineage()` keeps). **Live push (`app/live_push.py`) is same-origin SSE through each portal's BFF** — the portal mints a single-use ticket with its server-held bearer over private `API_URL`, opens the API stream with that ticket in `x-realtime-ticket`, and pipes it to browser `EventSource`; no browser needs an API origin, bearer or ticket. The old WebSocket endpoint (`/messaging/ws`, `/notifications/ws`) has been removed. The bounded per-reader queue collapses overflow to a `resync` signal, the stream heartbeats every 15 seconds, and reconnect/resync refetches the source of truth. Its registry is still in-process and needs Postgres `LISTEN`/`NOTIFY` to survive more than one API instance; `push()` runs every payload through `jsonable_encoder` once before either transport, since a raw `datetime` in a message row used to fail every send silently. The platform inbox's read state follows what's actually on screen, not merely which conversation is open — a push for the open conversation only auto-marks-read if the thread was scrolled to the bottom when it arrived, matching Slack/Teams. **Attachments (0081_messaging_attachments, then `0123_messaging_multi_attachments`)** are ANY NUMBER of files on one message (pdf/word/excel/powerpoint/txt, 25 MiB each, magic-byte sniffed — never the declared Content-Type — via an extended `app/storage.py` allowlist: OOXML disambiguated by internal zip parts, legacy Office by its one mandated OLE2 stream via `olefile`, text accepted only by elimination), stored in the TENANT'S OWN bucket under a private `files/{contact_uid}/messages/{attachment_uid}.{ext}` key (never the shared documents bucket, never the public `files/tenant/` prefix), uploaded through a `CappedBodyRoute`-capped multipart endpoint (the same unbounded-multipart-spool gotcha `routers/documents.py` guards against), and downloaded only via a same-origin proxied stream fetched on click — list responses carry attachment metadata only, never bytes or a URL. **0081's one-per-message cap was UX, never a domain rule, and unwinding it took four agreeing parts, three of which were wrong on their own:** the storage key had to become per-ATTACHMENT (message-keyed, the second file overwrote the first), both composers had to stop looping (the client portal's still did, so a client attaching three documents produced three bubbles, and a mid-loop failure left some sent and some staged), and all three SvelteKit proxies had to rebuild the body with `getAll('file')` — `get` returns the FIRST part only, so a three-file send uploaded one and reported success, invisible from either end. Each proxy carries its own test, because they are separate files that merely happen to agree. **The client record's Messages section also carries a right-hand rail the inbox does not** (people · files · open requests · open tasks — it only makes sense where the client is fixed by the surface): its visibility is `hidden lg:block` CSS with a reader override rather than measured state, so it is right before hydration and cannot flash; its Files panel derives from the LIVE `messages` `$state` both `send()` and the realtime push mutate, because a fetched list goes stale on the first send; and tasks are narrowed by the shared `isOpen` (open OR in progress) rather than by `task_status=open`, which would have hidden exactly the tasks somebody had started.
