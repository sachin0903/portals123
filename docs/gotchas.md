# Gotchas (hard-won, do not relearn these)

Platform traps that cost real time to find. Each one is here because it was hit at least
once and the symptom did not name the cause — a green gate, a silent no-op, an error that
pointed somewhere else. Read this before debugging tooling, and add to it when something
here would have saved you an hour.

- **Every session showing the same internal IP is the portal's TCP peer, not WorkOS.** Sign-in is server-to-server, so WorkOS stores the address the portal sends (`readSignInClient` → `getClientAddress()`). The node adapter uses a forwarded header only when `ADDRESS_HEADER` is set; the portal block set `PROTOCOL_HEADER` and `HOST_HEADER` and not that, so the address was Traefik on the Docker network. `ADDRESS_HEADER=x-forwarded-for` and `XFF_DEPTH=1` take the hop that proxy appended. A session already open keeps the old address until the next sign-in. A second proxy in front of Traefik makes depth 1 that proxy's address — do not bump the depth to skip it.
- **A platform LCP landing ~2s after load on every page is the firm logo, not the page.** The shell paints `logo_url` in a 28px slot; on staging that was a 3481×624 PNG held as a base64 `data:` URI (the no-object-storage rung of `put_branding_asset`), and decoding the bitmap on the main thread was the Largest Contentful Paint on 29 of 30 pages — the dashboard escaped only because a hero figure is larger than the logo. A data URI cannot be cached, resized or deferred, so no header or `loading` attribute helps. Uploads are now stored display-sized (long side ≤ 1024px, `app/shell_images.py` — the wordmark's width on a 3× display, not the 36px slot height; 256px was below the painted size and the sidebar and login splash looked soft), the portal payload and `/internal/admin-branding` withhold an inline raster over 32 KiB / 1024px (the shell shows the built-in mark), and `logoSources` in `pkgs/ui` refuses one again. An existing inlined logo still has to be moved onto the relay with `scripts/restore_inline_branding.py`; until then the firm sees the built-in mark, not its own. `docs/storage.md` §8.
- **A Seccl parquet 404 `NoSuchBucket` on `s3://platforms/…` is the external store, not `createbucket`.** That one-shot aliases `http://rustfs:9000` and production does not start it (or the bundled RustFS). The catalogue path can be right and the write still 404s because the bucket was never created on `S3_ENDPOINT_HOST`. The GitHub Environment does not have the object-store secret (`render_app_env.py` drops `S3_*`); `deploy-prod` decrypts `vault_portals_s3_secret_key` and runs `rustfs/rc` on the pipeline host before `app_stack`. Adding `createbucket` to `app_stack_pipeline_services` starts the spare RustFS and fails the deploy wait, because that job exits.
- **A sign-in that works one time in three on a firm's own domain, with the MFA code "wrong" and then "timed out", is a stale verification registry on the other API replicas, not WorkOS and not the authenticator.** `tenant_registry` is per process, prod runs one API per site behind Cloudflare, and `POST /admin/environments/refresh` reaches only the replica that served it. A firm registered after boot is unknown to the others, which verify its tokens against the fallback project's JWKS — the API log is `Access token verification failed: Unable to find a signing key that matches "sso_oidc_key_pair_…"`, in bursts of dozens per page load. On the MFA step the code is accepted (pending token consumed), `GET /me/portal` 401s, the portal revokes the new session and shows "unavailable"; the retry of the same code is `Invalid one-time code`, then `pending_authentication_token has expired` → `/login?expired=1`. The registry now reloads itself on a miss (`tenant_registry.resolve`, throttled, single-flight); before that fix the only cure was restarting the API container on every site. Check the per-site API logs, not the portal's, and check all three.
- **Demo book-cost dashes next to a working Cash figure is a DuckLake column type, not missing seed maths.** The holdings extract has market value and no cost; `_source_book()` stamps `book_cost` / `unrealised_gain` as floats and the lake write copies them. If the tenant's `platform.positions` was first created with those keys as `None`, DuckLake infers a NULL-typed column and `CREATE OR REPLACE TABLE` does not widen it — later floats land as SQL NULL. The header then dashes (no cost on any row) and Growth shows `+£0.00` (`_num(null)`), while Cash still works because `market_value` was numeric from day one. The write now `DROP`s the relation first; the demo reader also fills leftover NULLs from the valuation series. Re-seed (or just reload — the reader fill does not wait for a re-seed) after pulling.
- **Every Seccl client appearing twice is the shared landing table, not Seccl creating people twice.** Seccl, SEI and Morgan Lloyd used to ReplaceInPlace the same `inbound.{uid}__clients`. The merge stamps whatever is sitting there with the provider it was called as, and it runs after staging, so another daemon can overwrite the table in between. On 27 Sep 2026 SEI's merge ran three seconds after Seccl's and inserted Seccl's 304 clients (and 52 models) under `provider = sei`. The landing schema is now the provider's (`inbound_seccl`, `inbound_sei`, `inbound_morgan_lloyd`, migration 0209) because the table name is already 60 of Postgres's 63 bytes. A SEI client list that is empty after that fix is the other half: `RESIDING_SUBFIRM_ID` is blank on the whole Clients report, so filtering `subfirm_id` matched nobody. The slice uses `subfirm_ids`, the subfirms of the accounts the client holds.
- **An empty warehouse after `pnpm db:reset` while sei/seccl `:dev` only logs `GET /plan` / `GET /runs` 200 is a daemon that was not restarted, or a startup run that was skipped.** A start runs `interlace serve --no-apply` and then enqueues one full `POST /runs {}`. `CronTrigger` still waits until the next slot (SEI 05:00 Tue–Sat, Seccl 02:00) and never fires on first sight, so the startup run is the boot. It is skipped when a run is already in flight, when one succeeded inside `SYNC_ON_START_DEBOUNCE_SECONDS` (default 30 minutes), or when `SYNC_ON_START=0`. `api:db-reset` deletes `services/*/.interlace/{state,streams}.db` after `down -v`, so the next start is not still pointing at snapshot tables the volume wipe destroyed — but a daemon left running keeps the old file open until it is restarted. Sync is `POST /runs`, not `interlace apply`.
- **A SEI run dying on `lake_{hex}.projection` / `Table with name nodes does not exist` was `replace` dropping the DuckLake table mid-apply.** Virtual `replace` rebuilt the relation by dropping it; the lake Python model then ATTACHed DuckLake before promotion, so `platform.nodes` was gone in-session. Conformed snapshots and tenant slices now `full_merge` on their published key (missing keys still disappear; the table does not). The projection still skips a missing core table so a half-promoted catalogue cannot abort the run. Sync is `POST /runs`, not `interlace apply` — the models list's rebuild/refresh badge is the compiled _plan_ for the next run.
- **`platform.positions` failing both `unique_external_id` and `unique_position_key` is two listings with a blank taxlot, not a split lot.** A split taxlot fails only `position_key`: `external_id` carries the taxlot, so the two lots stay distinct while each takes a copy of the supplement. Production 2026-10-06 failed both, two groups each. `TAXLOT_ID` was null, and `concat_ws` skips nulls, so the taxlot dropped out of `external_id` and two `TRD_INSTRUMENT_ID`s of one `INSTRUMENT_ID` shared it. The supplemental is per traded instrument and the join omitted that column, so each line was paired with both gains. The keys now keep an empty segment for a blank taxlot and include the traded instrument; `position_key` still omits the taxlot, so a real split still stops the night. Do not collapse the two lines into one holding.
- **Do not give `platform.valuations` an `external_id` of `account:YYYYMMDD`, or a `unique: external_id` check.** A valuation is not an entity with its own provider id. The lake grain is `(account_external_id, as_of_date)`; the book already keys `(account_id, as_of_date, source_system)`. The 158 failures on 14 Oct 2026 were not two valuations: every pair was one account on one day, and the only column that differed was `unrealised_gain`, by a unit in the last place (`-23548.99` beside `-23548.989999999998`). DuckDB's `/` on decimals returns DOUBLE, so the lot conversion was a float and the sum of those floats was not the same value on `full_merge`'s two reads; both copies were stored. Each lot is rounded to the report's scale before the sum. Putting the composite id back, or summing the raw doubles, recreates the block.
- **`platform.instruments.unique_external_id` blocking a SEI rebuild is a tied window, not two instruments.** `full_merge` reads the model twice (changed keys, then the insert). The Assets report repeats an instrument per listing, and a pick ordered only by name / ISIN / SEDOL ties when those three match. The two reads can keep different listings, both get written, and the check reports that many failing keys — promotion of the whole run stops, including every `book_*.merge_ledger`. The order has to end in `raw.assets`' own key (`_source_file`, `_row`) so both reads keep the same row.
- **`moon run :dev` stuck after a file save is the API waiting on SSE, not a dead file watcher.** WatchFiles logs "Reloading…" then "Waiting for connections to close" and never comes back: the platform tab holds `GET /notifications/events` (and chat) open, and uvicorn's default graceful timeout is forever. `python -m app` now passes `timeout_graceful_shutdown=1`. A process already stuck will not pick the change up — CTRL+C `:dev` and start it again.
- **A pending Graphene transaction is not an unclassified credit.** `0197` writes
  `source_system = graphene` rows for booked contributions, transfers and payment instructions.
  The unclassified queue and the matcher look at `type = deposit` with `expectation_id IS NULL`;
  without excluding graphene, a booked £800 contribution would classify as a new credit of the
  same amount (or match itself). `matching.py` filters `source_system <> 'graphene'`, and unlink
  detaches only the inbound `matched_transaction_id`, never the Graphene sibling. Do not rewrite
  `source_transaction_id` to a vendor group id: the book-sink upserts on that pair. Vendor ids
  go on `platform.links`. `docs/transaction-status.md`.
- **A DCube drawdown SSO URL that 500s is CTC `SSOLogin`, not our mint.** `POST /cam_setmemberdetails` still returns `ssoUrl`. The SPA at `digitaltest.ctc.uk.com` is HTTP 200; component `H5` then `form.submit()`s `{providerSSO, loginId, ssoToken, policyNumber}` (nulls included when the hash omits a key) as form field `data` to `https://digitaltest-api.ctc.uk.com/api/DrawdownSetup/User/SSOLogin`. That call 500s with an empty body and no `content-type` — confirmed from the live tab, CORS-readable, so the body really is empty rather than hidden. `cam_validatesso` on the same token returns `responseKey` 0, and the 500 still happens with the `generate_illustrations.py` CTC1 document (XML declaration + `Drawdown`) as well as our Flexi Access template. A spent `ssoToken` is DCube's "Login failed" page, not 500. Two things that look like this 500 and are not: (1) missing `illustrationTemplate` — DCube asks for it _after_ login via `DrawdownSetup/Illustration/IllustrationDocument`; (2) a scheme with no policy valuation — `cam_memberdetails.assetValuation` stays 0 until `cam_createpolicyvaluation` has been filed (create-time `assetValuation` and `cashValuation` are ignored). Filing the wrapper policy still leaves `cam_getscheme.fundsLastCalculatedDate` at year 1 and `uncrystallisedFundAmount` / `cam_memberdetails.uncrystallisedValue` at 0 until ML's next-working-day roll-up. CTC's API process is up (`User/Details` is 405 on GET). Under 55 there is no DCube journey at all (paper ill-health). ML's `ssoUrl` omits `policyNumber`; DCube reads it from the hash query (the policy `cam_createwrapper` minted). The remaining 500 is CTC-side and **does not depend on the member**. Form `data` that is valid JSON — including `{}` and nil GUIDs — is always 500 empty; only a non-object (`""`, `"not-json"`, a JSON array) is 400 `Invalid request`. Other CTC endpoints (`User/Login/Create`, `Authentication/RequestNewToken`) return a normal 401 problem+json, so the API host is up and `SSOLogin` specifically is crashing. Raise that with CTC/Morgan Lloyd; minting another Graphene contact will not change it.
- **Seeded accounts showing a value and an empty holdings list is the catalogue, not the book.** Holdings are read from the tenant lake as `lake_reader`. The demo seed's DuckDB attach creates that schema as `lake_writer` and does not grant `USAGE`, and provisioning only grants it when `DATALAKE_DATABASE_URL` is already set. Either miss makes `_firm_read` degrade to nothing — a seeded book does not fall back to the dev extract — so the account value (OLTP) is there and the holdings table is empty. The seed now grants before it writes. A book already seeded needs `GRANT USAGE ON SCHEMA "<tenant uid>" TO lake_reader` (and `SELECT` on its tables) in the `datalakes` database. The API also needs the three `DATALAKE_*` lines from `docs/datalake.md` §6 in `apps/api/.env.local`; it does not read the root `.env`. Restart the API after adding them.
- **Client search stuck on “Searching…” after the request has returned is a duplicate list key.** The palette keys each hit on `type` + `id`. A holding id used to be the instrument key, and the same fund on two accounts is two rows with that one key. Svelte throws `each_key_duplicate` and rolls the update back, so `loading` stays true and the panel never leaves “Searching…”. The id is now `account uid` + instrument, and the list key also carries the account and the row index.
- **Client-portal search finding accounts but no holdings, while the holdings page lists them, is the reader map.** Spotlight calls `search_firm_holdings`. The holdings page calls `firm_holdings`. Only the second was registered with the demo lake and the dev-extract fallback, so a seeded book — and a firm whose warehouse slice cannot be read — searched the provider catalogue, got nothing, and the palette dropped the empty group. Both maps now include the search reader (`app/lake/demo.py`, `app/lake/fixture.py`).
- **A seeded Graphene client login seeing 0 accounts is usually the link, not the book.** `/crm/home` (the composed portal's accounts cards) only admits `platform.links` rows whose provider is a **custodian** (`seccl`/`sei`) or `data.seeded_demo`. Demo seed used to take `ORDER BY provider LIMIT 1` from `tenant_platforms`, which on Graphene is Morgan Lloyd — a scheme administrator — so staff still saw the four wrappers and the client portal showed none. The other empty-portal shape is a login with no `crm.contact_users` row for the WorkOS user they actually signed in as (`auth.resolve_claims` then mints empty `contact_ids`; reset-and-seed also clears that table). Check `platform.links.provider` on the demo accounts and `crm.contact_users` for the login before assuming the seed wrote no rows.
- **Client-portal wrapper cards saying "Account" is `products_read`, not missing seed data.** `/crm/home` takes `type` from `platform.products.product_type` and falls back to `"Account"` when the join is NULL. `0042` keyed that table on `tenant_lineage()`, which is empty for a client, so every firm-scoped ISA/SIPP/GIA badge became "Account" while the account _name_ (on `platform.accounts`) was fine. **0177** adds `auth.tenant_id()` (the 0082 lever). Staff never saw this because they have lineage.
- **Studio “Saved.” with the old client portal after refresh is two layers, not one failed PUT.** The Pages canvas writes a local working set; `$state.snapshot(drafts)` has omitted a `pages` property assigned onto an existing draft, so the action toasted success while the body echoed the previous composition (`withWorkingPages` stamps the dirty working set onto the JSON PUT). Separately, `resolveEnvironment` caches `/internal/env-config` for 60s. **Only the branding editor routes bypass that cache** (`/branding` on platform; `/tenants/{uid}/branding` on admin, including the admin-brand logo cache), so a Studio save is on the next paint of that page. Every other navigation — including the client portal — uses the TTL; a client-portal paint may lag the studio by up to 60s. A design set with no pages of its own must also **keep** `Branding.pages`; deleting then copying `null` hid the parent composition and sent every client back to the platform defaults.
- **A conditional field that never reveals on a ticked checkbox is a DOTTED FIELD KEY, not the operator.** The form runtime keeps answers flat by `fieldKey` (`values['pension.hasEmployerContributions']`) while `getNestedValue` walked a condition's `field` as a PATH (`values.pension.hasEmployerContributions` → `undefined`, which every operator reads as "no"). The seeded employer step revealed its company fields on exactly that condition, so ticking the box showed nothing and no employer was ever captured — and the API's `missing_required` skips conditional fields, so the submission went through blank. `getNestedValue` now tries the exact key first (as the mapper's `_answer_for` always did). A conditional keyed `a.b` that still misfires: check whether the answer is stored flat or nested, and remember the two disagree by design for composite fields (`address` stores `{address: {line1}}`).
- **Two applicants' copies of the same journey form leaking into each other is the page identity, not the store.** Answers are keyed by `request_item_id`. Joint onboarding fans Applicant details into two profile cases that share `form_uid` and `step_key`. The staff form page keyed `form_uid:step_key`, so Prev/Next reused applicant 1's in-memory `values` and submitted them onto applicant 2. Identity is `case_uid:step_key:participant` (`stepFormIdentity`).

- **A SvelteKit `redirect()` inside a `try` is swallowed by its `catch`.** `redirect(303, …)` (and `error()`) THROWS; a `try { … redirect(…) } catch { /* fail open */ }` around an API call catches the redirect too, so the branch that was meant to bounce becomes a no-op and nothing logs. The client portal's login terms gate was written exactly that way and never fired (the local demo client had two unaccepted Graphene documents and browsed the portal freely; the pages loaded fine, so nobody looked). That gate was removed on 13 Oct 2026 — terms are collected inside a journey, and no portal calls `GET /terms/outstanding` on navigation — but the trap remains. Decide inside the `try`, redirect outside it, or keep the fetch in a helper that returns a value and never wraps control flow.
- **A colon-name in a SQLAlchemy `text()` comment is a missing bind, not a comment.** `text()` scans the whole string for `:param`, including `--` comments. A note that said "do not write `:set` here" became `bind parameter 'set'` on every `set_product_platform` call. The same scan is why `:due::date` / `:data::jsonb` are left literal (`::` after a bind is treated as a Postgres cast, so the parameter is never bound) — use `CAST(:due AS date)` / `CAST(:data AS jsonb)`, and keep colon-names out of SQL comments. `app/matching.py` records the cast trap; `tests/test_catalogue.py::TestProductPlatformSettings` is the tripwire, because it EXECUTES the statement.
- **A `/*` inside a DuckDB `--` comment is an unterminated block comment, not a glob.** interlace rewrites each `--` line as `/* … */` before DuckDB sees it, and DuckDB nests block comments. `platform.portfolios` said `PSM/model/assignment/*` in a header note; the warehouse failed with `Parser Error: unterminated /* comment` while `test_platform_portfolios` stayed green because it executed the `--` form. The tripwire now rewrites comments the same way before `_build`. Do not write `/*` or `*/` in a `--` comment in a DuckDB/interlace model.
- **SEI account-template listing 404s on the Swagger spelling.** `GET /enrollmentAccountTemplates/…` (camelCase `A`, concatenated from `servers.url` in `swagger-spec-EnrollmentAccountTemplates.yaml`) is `Unable to identify proxy for host: sei-default`. The sibling client service is documented — and deployed — as all-lowercase `enrollmentclienttemplates`, and that is the proxy name Apigee has for both. `GET /enrollmentaccounttemplates/crm/account/templates` is 200 (Blackfinch AIM ISA / AIM IHT). Same class as `getAccountDetailsinfo`: the gateway's spelling is the one that exists. `pkgs/sei/tests/test_endpoint_paths.py` refuses the camelCase path so it cannot come back.
- **SEI client-document URLs are all-lowercase; camelCase is the proxy 404.** Verified i31 22 Sep 2026. `POST /retrieveendclientdocumentservice/documents/list` is a business response (200 `documentList`, or 400 `Invalid entity ID` for a party that does not exist). `POST /docretrievecontentservice/` reaches `/rest-doc-mgmt/documents/retrieveDocumentContent`. `retrieveEndClientDocumentService` and `docRetrieveContentService` 404 `Unable to identify proxy for host: sei-default` — the same trap as `enrollmentAccountTemplates`. `x-sei-enabled: false` on both operations is stale. The US-tax sibling is the exception that keeps a capital S: `docretrieveustaxService` (all-lowercase 404s); we do not call it. A 404 on the lowercase path still fails the run rather than looking like a firm with no statements. There is no firm-document endpoint: `includeFirmGenericDocs` returns a group named `Firm Generic Documents` on the same per-party list. Those are filed once per tenant of the firm with a null contact. A client document waits until `platform.links` has that party — filing it before the contact exists would point the library at nobody. `docs/sei.md` §1a.
- **SEI `firmemployeeusers` 400 `processingOrgId` is not an optional-scope call.** OpenAPI marks `processingOrgId` and `serviceId` `required: false`; live i31 400s without both (100014 "Prcossesing Organization Id is required", then 100015). `processingOrgId` is **not** the firm id: Blackfinch `3102`'s processing org is `3100` ("IWA Market 7") on `GET /cachereadservices/firm-default-attr-cache`. Sending `3102` is HTTP 200 with zero rows, which a `replace` model would read as "this credential has no employees". `serviceId` is a product-service filter, not a DSR tag (`59267` is "Service Id is Invalid"). Service `1` is a superset of every other populated id in 1–250 (312 users, all with emails); the spec's example `152` is empty. The sweep resolves the org from each firm on the Reference report (`ref.firms`), then pages once per distinct org with `SEI_SERVICE_ID` (default 1). The refuse-to-delete guard stays: empty plus failures must not wipe `ref.employee_users`.
- **DML in a migration over a FORCE-RLS table is a NO-OP THAT REPORTS SUCCESS unless it runs as `service_role`.** The migrator is not BYPASSRLS and `FORCE ROW LEVEL SECURITY` binds the table's OWNER too, so a backfill sees the rows its (absent) `request.jwt.claims` allow — none — updates zero rows and commits happily. `SET LOCAL ROLE service_role;` before the DML is the fix and 0059 documents it for `platform.products`; it has still been hit twice since. **0128** re-hit it (`INSERT ... SELECT` over `platform.products` inserted nothing because its own SELECT was filtered empty), and **0127** hit a nastier variant on `crm.contact_notes`: there the filtered `UPDATE ... WHERE uid IS NULL` reported `UPDATE 0` and the very next `ALTER COLUMN uid SET NOT NULL` — which validates EVERY row, policy or not — failed with "contains null values" against rows the same transaction had just been told did not exist. The shape to copy for a new NOT NULL column is a defaulted `ADD COLUMN` (`nanoid` is VOLATILE, so the rewrite evaluates it per row and never reads through a policy); for real DML it is `SET LOCAL ROLE service_role`. **The test suite cannot catch either**: it builds every database from scratch, where the table is empty, the backfill has nothing to miss and NOT NULL is satisfied trivially — both reproduce on the first database with a row in it.
- **A LISTING THAT FEELS SLOW IS USUALLY RLS EVALUATING ITS HELPERS ONCE PER ROW, and the cost grows with the book.** Every scoped policy in this database is written in the shape `auth.can_read_all() AND tenant_id = ANY (auth.tenant_lineage()) OR account_id = ANY (auth.account_scope()) OR ...`. Those helpers are `STABLE`, but a bare call inside a policy predicate is evaluated **per row**, so the cost is O(rows) even for a query that returns twenty-five of them. Measured on `platform.transactions` at 8,261 rows, all three returning the identical set: `SELECT count(*)` as `service_role` **0.96 ms**, under RLS **279 ms**, and under RLS with each helper wrapped in a scalar subquery **4 ms**. That is ~290x and ~70x on a `count(*)`; the real listing query, which joins accounts, contacts and advisers and is followed by a Python filter/sort/page over the whole match set, measured **1.9 s** end to end from the portal's loader. The fix is the documented Postgres pattern and nothing more: wrap each helper so the planner runs it once per statement — `((SELECT auth.can_read_all()) AND tenant_id = ANY ((SELECT auth.tenant_lineage())::integer[]))`. **The cast is required**: the helpers return `integer[]`, and `= ANY (subquery)` is parsed as the set form, which fails with `operator does not exist: integer = integer[]` — a bare `(SELECT ...)` alone will not compile. **136 policies** carry the unwrapped shape today (`SELECT count(*) FROM pg_policies WHERE (qual || coalesce(with_check,'')) ~ 'auth\.(can_read_all|tenant_lineage|account_scope|contact_scope)\(\)'`), so this is a whole-estate rewrite rather than one table's problem, and any rewrite has to assert the row count per role is unchanged before and after — the semantics must not move, only the evaluation count.
  **WHAT MAKES THIS EXPENSIVE TO FIND: every obvious way of measuring it hides it.** A test suite builds each database from scratch, so the table has too few rows for the per-row cost to show. A router test, a `TestClient` run with `dependency_overrides`, and any profiling script that opens its own session all run as `service_role` or with the auth dependency replaced — and `service_role` does not read through policies at all, so the endpoint measures as _fast_ by exactly the layer at fault. A `psql` session likewise bypasses it unless you `SET ROLE authenticated` **and** publish a realistic `request.jwt.claims`. This was hunted through the API, the ORM, the data lake, SvelteKit streaming, the Vite dev server and component mount cost before the policy was suspected, because each of those measured clean. To reproduce it, do what the request does: `SET ROLE authenticated; SELECT set_config('request.jwt.claims', '{"portal":"platform","permissions":["contacts:read_all"],"tenant_id":<id>,"tenant_ids":[<id>],"user_uuid":"<uuid>","account_ids":[],"contact_ids":[]}', false);` and time the read both ways in one session.
  **The second half of the same defect is the endpoint shape.** `crm.py`'s listings read the WHOLE visible table, then filter, sort, facet and page it in Python (`list_transactions`, `list_contacts`). That is what turns a per-row policy cost into a per-request one, and it is why transactions is the worst of them — it is the largest table read this way. Fixing the policies takes the 1.9 s to roughly 0.2 s; pushing the filter/sort/page into SQL is the deeper fix and a much larger change, and the two are independent.
  **Where this stands.** #190 did the endpoint half (MATERIALIZED CTEs, one statement) and left the policies, so the listing still paid ~1.07 s for `transactions_read` on 8,141 rows; `0230` wraps `transactions_read`, `accounts_read` and `links_read` and nothing else, so the other policies above still carry the per-row shape. **A correlated subquery in a listing's SELECT undoes a CTE fix silently**: `798baaab` added `custodian` to the transactions listing as `_RESOLVED_CUSTODIAN_SQL`, a lookup on `platform.links` that ran once per transaction row (8,141 runs through `links_read` for ~40 accounts, ~1.1 s), four days after #190 had made the page fast. Anything per-account or per-client in `list_transactions` belongs in a MATERIALIZED CTE joined in, as `advisers`, `live_contacts` and `account_custodians` are.
- **A QUERY THAT RUNS IN 50 MS BUT TAKES 1.5 S IS POSTGRES JIT, AND RLS IS WHAT SETS IT OFF.** JIT is a server default (on since Postgres 12; nothing here chose it). It compiles any statement whose ESTIMATED cost passes `jit_above_cost` (100k) and optimises and inlines past 500k, and the compiled code is not cached, so the cost is paid on every execution. A policy subquery the planner cannot index is costed as a scan per row, so the estimate is fiction: `GET /documents` joined `documents.files`, whose read policy was then one EXISTS over `documents.documents` with a three-way OR, and with only a few hundred documents the planner put it at 1.4M+ — **~1.4 s of `JIT: Timing` on a ~50 ms statement**, with the time charged to whichever plan node first runs compiled code (here the `documents` seq scan), so the node timings point at the wrong place.
