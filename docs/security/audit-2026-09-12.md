# Security audit — platform portal & API (Sep 2026)

**Scope:** `apps/api` (FastAPI), `apps/platform` / `apps/client` / `apps/admin` (SvelteKit),
`pkgs/auth`, `pkgs/ui`. Focus on the platform portal's real risk surface: tenant isolation (RLS),
authorization, input validation, injection/SSRF, and output encoding (XSS).

**Method:** manual black-box probing of the staging/dev deployments plus a code-level review across
four dimensions (authorization/IDOR, RLS policies, injection/SSRF, XSS/secret-exposure). Every
candidate was verified against the source before being recorded; plausible-but-wrong candidates were
dropped (see _Non-findings_).

**Authorization note:** all testing was performed by the platform's own developer against
non-production environments. Destructive/DoS-class tests are flagged and were **not** run against
shared infrastructure.

## Findings

### 1 — Document upload OOXML type-confusion · Medium · reproduced

**Where:** `apps/api/app/storage.py::sniff_document_type`.

**Gap:** the document-library upload path validated ZIP-shaped uploads by trusting the client's
**declared** Content-Type (`if declared == DOCX: return DOCX`) instead of inspecting contents. Its
sibling `sniff_attachment_type` did the correct thing (`_ooxml_kind` opens the zip and requires a
real `word/`/`xl/`/`ppt/` part). So any zip at all — a renamed archive, an `.xlsx`, arbitrary bytes
— could be stored as a `.docx` by claiming to be one.

**Impact:** defeats the "PDF/Word only, magic-byte verified" control on the primary document path.
Realistic harm: malware **delivery/staging** through a trusted internal channel (files are served
back as `.docx` downloads and can be sent to clients via `documents:send`); AV/DLP bypass; latent
escalation to zip-bomb/zip-slip/XXE the moment any feature parses these as real OOXML. Requires
`documents:write`. Not RCE on its own; not XSS (smuggled zips are served `attachment`, never inline).

**Reproduction (confirmed):** upload `impostor.docx` — a valid zip with no OOXML parts (just a
`note.txt`) — via the client Documents tab / `POST /documents?/upload` with `document_type` = a real
docx type. Accepted and stored.

**Fix:** `sniff_document_type` should derive type from content via `_ooxml_kind(data)` and accept
only a genuine `.docx`; drop the `declared` parameter (also from `validate_upload`; 3 call sites).
Add regression tests with real zip fixtures. _(This fix was applied and green earlier, then lost
when the working tree was reset — re-apply.)_

### 2 — "Read-only" DuckDB SQL console → local file read + SSRF · High · REPRODUCED

**Where:** `apps/api/app/platforms.py::_query_sync` + `apps/api/app/lake/core.py::connect` (the
`INSTALL/LOAD httpfs` with no `enable_external_access=false`); exposed at
`POST /admin/platforms/{provider}/query` (internal API), reached via the operations portal proxy
`POST /platforms/{slug}/query/run`, gated `platforms:query`.

**Gap:** the console accepts arbitrary `sql` and defends only against multi-statement (`;`) and
non-SELECT input. The DuckDB connection loads `httpfs` with no `enable_external_access=false` /
`lock_configuration` / `disabled_filesystems`. `READ_ONLY` applies to the attached catalogue, **not**
to DuckDB's scalar/table functions — so a single `SELECT` reaches the local filesystem and arbitrary
HTTP/S3.

**Impact:**

- Local file read → **process secret exposure**: `read_blob('/proc/self/environ')` leaks
  `DATABASE_URL`, `BOOK_WRITER_DSN`, `S3_SECRET_ACCESS_KEY`, `SECRETS_MASTER_KEY`, `WORKOS_*`,
  `ANTHROPIC_API_KEY`, etc.
- **SSRF** / cloud-metadata: `read_csv('http://169.254.169.254/latest/meta-data/iam/...')` →
  instance-role credentials.
- `read_parquet('s3://…')` beyond per-firm schema separation via the core S3 credential.

Requires `platforms:query` — deliberately split out of `platforms:read` to be a grantable "curated
SQL console", so an ops user given _only_ it gains host-level file read + SSRF.

**Reproduction (CONFIRMED on dev):** in the operations portal's Query console for a provider
(`/platforms/{slug}/query`):

```sql
SELECT content FROM read_blob('/etc/hostname');
-- → b'23e76f87b9aa\n'   (the container's own hostname, read from the host filesystem)
```

The console returned the file's bytes → arbitrary local file read confirmed. (The
`/proc/self/environ` and IAM-metadata variants were deliberately NOT run — they return live
secrets.)

**Fix:** on the connection, before use, `SET enable_external_access=false;` +
`SET lock_configuration=true;` (or `SET disabled_filesystems='LocalFileSystem,HTTPFileSystem'`). The
DuckLake attach + `s3://` reads use the scoped secret, so external access can be disabled for ad-hoc
queries. Alternatively allowlist the query shape to `FROM {schema}.{relation}`.

### 3 — Branding upload: no request-body cap (authenticated DoS) · Medium · code-confirmed

**Where:** `POST /firm/branding/asset` (`apps/api/app/routers/firm.py`, `data = await file.read()`);
`POST /admin/tenants/{uid}/branding/asset` (`apps/api/app/routers/admin.py`,
`_store_branding_asset`).

**Gap:** neither router uses `CappedBodyRoute` / `storage.read_capped`; both read the entire
multipart body into memory before the 512 KiB `MAX_ASSET_BYTES` check inside `put_branding_asset`.
The email-template-image route in the same file fixes exactly this
(`route_class_override=_ImageUploadRoute`); the branding paths were missed. Every other upload path
caps correctly.

**Impact:** an authenticated `branding:write` / `tenants:write` caller can exhaust API memory /
temp-disk with a multi-GB body buffered before the cap runs.

**Reproduction:** DoS-class — do NOT run against shared infra. Confirm at code level or a controlled
local run. Verified by reading the source: `data = await file.read()` with a plain `APIRouter`.

**Fix:** add the capped route class to both branding routers (mirror `_ImageUploadRoute`), or use
`storage.read_capped`.

### 4 — Branding upload: declared-type trust + SVG allowed · Low–Medium · code-confirmed

**Where:** `firm.py` / `admin.py` pass `file.content_type` straight to `put_branding_asset`;
`storage.py::put_branding_asset` validates only that the **declared** type is in `_EXT` (which
includes `image/svg+xml`) — no magic-byte sniff, unlike every other upload path.

**Gap:** a `branding:write` user can store arbitrary bytes (e.g. an SVG carrying `<script>`) by
declaring an allowed type. Same class as Finding 1.

**Impact bounded by:** the same-origin asset proxy sets
`Content-Security-Policy: default-src 'none'; …; sandbox` + `nosniff`, neutering script even for a
directly-opened SVG. Residual risk is the anonymous-read bucket copy served without those headers —
impactful only if `public_base_url` is a cookie-sharing subdomain of the portal.

**Reproduction (safe):** upload an SVG containing `<script>alert(document.domain)</script>` as
`kind=logo`; fetch the returned `/_assets/{name}` (confirm sandbox CSP blocks it); if the tenant
bucket has a public base URL, fetch the direct bucket URL.

**Fix:** magic-byte sniff this path; drop or sanitise SVG; align with the "never trust the declared
Content-Type" rule.

### 5 — CSS injection via `style` attribute in insights articles · Low · reproducible

**Where:** `apps/api/app/content.py` (`_ALLOWED_ATTRS` has `"*": {"class", "style"}`), rendered at
`apps/client/.../insights/[uid]/+page.svelte` via `{@html item.body_html}`.

**Gap:** nh3 strips scripts/handlers/`javascript:` hrefs but does not sanitise CSS inside an allowed
`style` attribute (reproduced: `nh3.clean` returns the `style` value verbatim). `img src` also
allowed.

**Impact:** no script execution (CSS `expression()`/`javascript:` url() are dead in modern
browsers). Residual: CSS-based UI-redressing (overlays) and background-image loads
(tracking/exfil-of-viewing) in a firm-authored article shown to that firm's clients. Staff→client
trust boundary, so low.

**Reproduction (safe — no JS fires):** publish an insights article with body
`<p style="position:fixed;inset:0;background:red;z-index:9999">covered</p>`; open as a client → a
full-screen red overlay confirms the passthrough.

**Fix:** drop `style` from `_ALLOWED_ATTRS` (keep `class`), or post-filter CSS.

### 6 — Unsanitised `{@html}` of terms content · Low (latent) · not currently exploitable

**Where:** `apps/client/.../requests/+page.svelte` and `.../onboarding/+page.svelte` render
`{@html agreeDoc.content}`; source `documents.documents.metadata->>'content'` for
`document_type='terms'`.

**Gap:** rendered raw, un-sandboxed, in the client portal with no `sanitise_html` gate. Today the
only writer of `metadata.content` is the onboarding seed (constants), so not exploitable now.

**Impact:** none today; becomes a stored staff→client XSS if any future endpoint lets a firm
author/import terms HTML into `metadata.content`.

**Fix:** route through `sanitise_html`, or render in a `sandbox=""` iframe like email bodies.

### 7 — `notifications.*` missing tenant-containment FK · Medium · structural

**Where:** `apps/api/migrations/sql/0063_notifications.sql` —
`recipient_contact_id int REFERENCES crm.contacts(id)` (single-column FK) on
`notifications.notifications` and `notifications.preferences`; policies match
`recipient_contact_id = ANY(auth.contact_scope())` with **no tenant conjunct**; no composite
`(tenant_id, recipient_contact_id)` FK exists.

**Gap:** migration 0035 declared this pattern structurally impossible — every other client-scoped
table carries a composite `(tenant_id, contact_id)` FK. `notifications` (added at 0063, after 0035)
does not, and the producer writes as `service_role` (BYPASSRLS), so `WITH CHECK` doesn't backstop it.

**Impact:** a row with `tenant_id = FirmA` but `recipient_contact_id = (a FirmB contact)` would be
readable/mark-read-able by FirmB's client. **Latent / defense-in-depth:** contact ids are globally
unique and `contact_scope()` returns only ids the caller owns, so exploiting it needs a _producer_ to
write a mis-tenanted row — today's resolver uses the event's own same-tenant subject, so no confirmed
live path. One resolver bug away, with no schema backstop.

**Reproduction (DB-level):** as `service_role`, INSERT a notification with `tenant_id`=FirmA and
`recipient_contact_id`=a FirmB contact → succeeds (the equivalent insert on `messaging.messages` is
rejected by its composite FK — that contrast is the proof).

**Fix:** add `FOREIGN KEY (tenant_id, recipient_contact_id) REFERENCES crm.contacts (tenant_id, id)
ON DELETE CASCADE` to both tables.

### 8 — Schema-invariant test excludes six schemas (systemic) · Medium

**Where:** `apps/api/tests/test_schema_invariants.py` —
`SCHEMAS = ("auth", "crm", "platform", "flows", "documents", "tasks")`.

**Gap:** the three structural guarantees (RLS enabled+forced; every authenticated-readable table has
a policy; every client link is tenant-contained — the 0035 invariant) run only over those six.
`messaging`, `notifications`, `comms`, `aml`, `content`, `email` hold tenant-scoped tables and are not
audited. This is why Finding 7 slipped in.

**Impact:** the tenant-containment / FORCE-RLS / policy invariants are not enforced for new tables in
those schemas.

**Fix:** add `messaging, notifications, comms, aml, content, email` to `SCHEMAS`. Re-running then
fails on Finding 7 — turning the whole class into an enforced invariant. **Highest-leverage single
change.**

### 9 — Missing HTTP security headers (clickjacking confirmed) · Medium · reproduced

**Where:** platform portal responses. `apps/platform/src/hooks.server.ts` sets only `Accept-CH`/
`Vary`; no CSP in `svelte.config`/`kit.csp`; Caddy adds none.

**Gap (verified live):** `curl -sI <portal>/login` → `HTTP/2 200` with **none** of:
`X-Frame-Options`, `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`,
`Referrer-Policy`, `Permissions-Policy`.

**Impact:**

- **Clickjacking — confirmed:** the portal renders inside a cross-origin `<iframe>` (reproduced with a
  local harness). No framing protection → decoy-overlay attacks against logged-in staff (a tool
  acting on client money/PII).
- No CSP → no XSS defence-in-depth (compounds #5/#6). No HSTS → downgrade exposure. No
  `Referrer-Policy` → URLs (with uids) may leak. No `nosniff` on document responses.

**Reproduction (confirmed):** `curl -sI <portal>/login` shows none of the six headers; loading the
portal URL in an `<iframe>` renders (framing not blocked).

**Fix:** set headers at Caddy and/or `kit.csp`: `frame-ancestors 'none'`, `default-src 'self'`,
nonce/hash `script-src`, `object-src 'none'`, `base-uri 'self'`; plus Caddy `X-Frame-Options DENY`,
HSTS, `X-Content-Type-Options nosniff`, `Referrer-Policy strict-origin-when-cross-origin`,
`Permissions-Policy`. Apply to `client` and `admin` too.

**Status — Phase 1 applied (Sep 2026):** a shared `applySecurityHeaders()` in `pkgs/auth`
(`security-headers.ts`, exported from `index.ts`) now sets, on every response from all three portals'
`hooks.server.ts`: `Content-Security-Policy: frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN`,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and
`Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()`. This closes the
confirmed _cross-origin_ clickjacking hole while keeping same-origin iframes (admin template PDF
preview, HTML `DocumentViewer`). An existing CSP on the response is kept (the `/_assets` sandbox
is folded, not replaced). Unit-tested in `security-headers.test.ts`; `auth`/`platform`/`client`/
`admin` gates green. **The CSP is env-configurable** (`CSP_POLICY` / `CSP_REPORT_ONLY`, read at
runtime via `$env/dynamic/private`, documented in each portal's `.env.example`) so a fuller policy
can be trialled per environment with a Coolify env change + restart — no code deploy. A blank value
keeps `frame-ancestors 'self'`; `CSP_REPORT_ONLY=true` sends `Content-Security-Policy-Report-Only`
for tuning, and `X-Frame-Options: SAMEORIGIN` stays enforced regardless so report-only never reopens
the framing hole to other origins. The other four headers are hardcoded (safe defaults, not weakenable by a bad env). **Still pending:** (a) **HSTS** — deferred, to be set at the edge (Caddy/Coolify),
not version-controlled here; (b) **Phase 2** — a full `script-src` CSP via `kit.csp`, which needs the
injected theme/branding inline scripts noncing/hashing (else the no-flash theme breaks); when done,
fold `frame-ancestors` into `kit.csp` and drop the standalone CSP set in `applySecurityHeaders`.

## Hardening notes (not confirmed vulnerabilities)

### H1 — service_role tenant-scoping invariant unenforced by any test

Every `firm_session`/`aml_session`/`storage_session` handler must carry its own `AND tenant_id = :t`
(these run as `service_role`, bypassing RLS). Followed everywhere reviewed, but nothing structurally
prevents a future handler doing `SELECT ... WHERE id = :body_id` with no tenant predicate — a silent
cross-tenant IDOR. **Recommend a CI grep/AST check.** Spot-check: as Firm A staff, `POST
/contributions` with `account_id` belonging to Firm B → expect 404.

### H2 — Dev-auth bypass heuristic

`auth.py::_dev_bypass_allowed` (+ portals' `devPrincipal`) is guarded by `DEMO_AUTH_BYPASS` + a
non-production `APP_STAGE` allowlist, but the loopback/Host heuristic is spoofable behind certain
proxies. **Confirm on each deployment:** `APP_STAGE` not `dev`/`local`/`test` and `DEMO_AUTH_BYPASS`
unset. Test: send `Authorization: Bearer dev:eyJ...` → expect 401.

## Non-findings (verified safe — recorded so coverage is trustworthy)

- **Session cookie integrity** — truncating the last 1–2 chars of `wos-session-platform` appeared to
  bypass integrity, but those chars are a version suffix outside the Iron seal boundary; deeper
  truncation is correctly rejected → `/login`. No bypass.
- **Cross-tenant `/clients/{uid}` read** — foreign/nonexistent uid → 404, no data; no enumeration
  oracle.
- **Path traversal via upload filename** — storage keys are server-derived (uid + generated nanoid +
  sniffed ext); the client filename never touches the path.
- **CORS reflection** — safe on both surfaces. Portal (public BFF) returns **no**
  `Access-Control-Allow-Origin` for `Origin: https://evil.example` (live-tested: preflight + GET →
  200, no CORS headers). The API is not publicly exposed (internal `http://api:8000`; portals proxy
  server-side), and its CORS config pairs `allow_credentials=True` with an **anchored, canary-tested**
  origin regex (`config.py`) that refuses startup on `evil.example`/`null`/http/suffix-confusion.
- **Realtime (messaging/notifications)** — browser connects via `EventSource` to same-origin
  `/messages/events` / `/notifications/events` (portal BFF); the `api.*` URL is server-side only
  (`$env/dynamic/private`, never in the client bundle). Same-origin → no CORS surface.
- **Datasets `runQuery`** (`GET /datasets/{uid}/data`) — NOT free-text SQL. The `uid`/key is looked
  up in a Graphene-authored catalogue (`app/render/catalogue.py`), "never used to build a query";
  runs under the caller's own claims; `contact_id` RLS-validated. Free-text SQL was deliberately
  removed from this feature. Safe.
- **AML tipping-off control** (`aml.*`) — read policies `tenant_lineage`-only (+`is_system`),
  `contact_scope` omitted; client portal cannot reach `aml.*`; firm-side endpoint withholds undecided
  hits and `aml.hits.detail`.
- **`platform.products` scoping** — old `USING(true)` replaced with tenant-lineage check.
- **Automation `lookup` / webhook SSRF** — named-key operator allowlist; author never supplies a URL;
  redirects off; byte caps; JSON-only; response paths validated.
- **SQL identifier interpolation** (`platform_entities.py`, `platforms.py`) — relation/column/sort/
  join names are registry literals; `provider` validated against `PROVIDERS`; `uid` validated
  `^[A-Za-z0-9_]+$`; user values bound. No identifier injection.
- **Broken authorization / IDOR** — permission checks and tenant scoping applied consistently across
  all 35 routers; `?tenant=` proxy paths gate on ops-tenant + ops-portal + named permission;
  by-uid/int route ordering correct.
- **XSS sinks** — every `{@html}` is sanitised (nh3), sandboxed (`sandbox=""` iframe), escaped, or
  fed constant/developer input; Jinja renderer is `SandboxedEnvironment(autoescape=True)`;
  Content-Disposition strips CR/LF and percent-encodes. (Exceptions: #5, #6.)
- **Secret/PII exposure** — audit `REDACTED_KEYS` covers `*_ct`/password/secret/token/credential/
  api_key; secrets logged by length only; cookies `HttpOnly`/`Secure`(non-dev)/`SameSite=lax`.
