# Saved chart components + custom chart code — build plan

Two requests from the template editor, written up before either is built. They look like one
feature and are not: the first is **storage and reuse** of a configuration this editor already
produces, the second is **a second renderer** for shapes it cannot produce at all. The first is
low-risk and reuses everything; the second needs a security decision before a line is written.

Neither is started. This document is the thing to argue with.

---

## 0. What exists today, so the plan can be read against it

A chart or table in a template is a `<div>` carrying `data-comp-*` attributes
(`apps/platform/src/lib/components/templates/editor/marker-attrs.ts` lists every one). The editor's
config drawer edits a draft of those attributes and commits them in one `addAttributes` call.

On save, `serialize.ts` reads those attributes into `schema.components[]` — `{id, type, props,
binding}` — stored as opaque `jsonb` on `documents.template_versions.schema`. On render,
`app/render/components.py` matches each `<g-chart>` marker to its component by `data-id` and calls
`charts.py::render_chart_svg(comp, rows, width, height)`.

Two facts constrain everything below:

- **A component's configuration is already a self-contained JSON object.** `{type, props, binding}`
  plus the `data-comp-*` attributes it came from. Nothing else needs inventing to store one.
- **WeasyPrint has no JavaScript engine** (`docs/document-generation.md` §5.1). The PDF is built
  from static SVG. Any "custom chart" is authored SVG or it does not reach a document.

---

## 1. Saved components (firm-wide presets)

### What it is

An author configures a chart once — the firm's colours, its typography, its figure format, its
grid — and saves it as a named component. It then appears in the block palette, and dropping it
produces a chart already configured that way.

### Shape

**`0128_component_presets`** — a new tenant-scoped table beside the templates that use it:

```sql
CREATE TABLE documents.component_presets (
    id          int         PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    uid         text        NOT NULL UNIQUE,
    tenant_id   int         NOT NULL REFERENCES auth.tenants(id) ON DELETE CASCADE,
    code        text        NOT NULL,
    name        text        NOT NULL,
    kind        text        NOT NULL,   -- 'chart' | 'table'
    config      jsonb       NOT NULL,   -- the data-comp-* map, verbatim
    description text,
    archived_at timestamptz,
    created_by  uuid        NOT NULL REFERENCES auth.users(id),
    created_at  timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, code)
);
```

RLS in the same migration, like every tenant-scoped table. Reuses `templates:read` / `templates:write`
— a preset is a piece of template authoring, and a firm that can edit templates can already produce
the identical result by hand. No new permission.

### The one decision that matters: copy, not link

A preset is **copied** into the template on drop. It is not a live reference.

The alternative — editing a preset updates every chart already using it — sounds better and is a
trap. A template version is **immutable once published** (`0012_templates.sql`), and documents
already generated from it are regulated records. A live link would mean either a published version's
appearance can change under it (breaking that immutability) or the link silently stops applying at
publish (two behaviours for one concept). Copy has neither problem, and "update every chart" is a
feature that can be added later as an explicit, opt-in bulk action.

State this in the UI, once, where the preset is saved: _"Charts already using this keep the settings
they were given."_

### What a preset does NOT carry

`data-comp-data-source` / `-dataset-uid` / the field bindings. A preset is **appearance**, not data:
the same look applied to a different dataset is the whole point, and a preset that dragged a dataset
in with it would break the moment it landed in a template that has not linked it. The save dialog
strips them and says so.

Debatable: the axis labels and title. They are appearance by type and data by nature ("Fund Value
(£)" is about the series, not the look). Suggest **keeping** them, since a preset for a fund-value
chart wanting that label is exactly the case, and an author clears a text box faster than they type
one.

### Work

| Layer  | Change                                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| DB     | `0128_component_presets` + RLS                                                                                                                   |
| API    | `app/routers/component_presets.py` — list / create / rename / archive, `templates:*`                                                             |
| Client | regenerate `@graphene/api-client`                                                                                                                |
| Editor | "Save as component" in the config drawer footer; a **Firm components** palette category fed from the API; drop → `chartDraftFrom(preset.config)` |
| Tests  | API router + RLS; a unit test that a saved preset round-trips to an identical `data-comp-*` map                                                  |

Estimate: **1–2 days**. Nothing here is novel — it is the dataset CRUD shape with a different
payload.

## 2. Custom chart code

### What the code actually defines

Not the chart. The **marks**.

An earlier draft of this section had the author writing the whole SVG and looping over the rows
themselves. That is the wrong split: it hands them the expensive, risky half — data access, scales,
ticks, chrome — which is the half that already works.

A custom chart binds a dataset **exactly like every other chart**: the same Data tab, the same field
pickers, the same sample-values preview. The code says only how to draw what came back.

| The engine keeps                               | The code defines |
| ---------------------------------------------- | ---------------- |
| Fetching rows, resolving the bindings          | The marks        |
| The value domain and the nice ticks            |                  |
| The plot box, the axes, the gridlines          |                  |
| Title, legend, typography, background, palette |                  |

The consequence worth naming: **every control in the Appearance panel still applies to a custom
chart.** The colour pickers, the grid colour, the typography, the background — all of it is still
`charts.py`, so a custom chart is a chart, not a foreign object bolted into the page.

### The context handed in

`series` (the projected values, per series), `labels`, `x(i)` and `y(value)` (the scale functions the
engine already computed), `palette`, and the plot rectangle. Deliberately **no `rows`**: everything
the drawing needs is a number or a label that was going to be drawn anyway, and withholding the raw
records means the drawing layer has no reach into the dataset at all.

```jinja
{# Waterfall — each bar starts where the last one ended. #}
{% set ns = namespace(base=0) %}
{% for v in series[0] %}
  <rect x="{{ x(loop.index0) - 12 }}" width="24"
        y="{{ y(ns.base + v if v > 0 else ns.base) }}"
        height="{{ (y(0) - y(v))|abs }}"
        fill="{{ palette[0 if v > 0 else 1] }}"/>
  {% set ns.base = ns.base + v %}
{% endfor %}
```

Ten lines, because the engine has already done everything around it.

### What this does and does not reach

**Does:** anything that is marks in a normal x/y plot — waterfall, bullet, candlestick, dumbbell,
stepped line, range band, target markers.

**Does not:** anything with its own geometry — a gauge, a radar, a sankey. Those need to own the
whole canvas, which is the expensive version this section used to describe. If one of those is the
actual requirement, it is a separate decision and a separate estimate.

### Security, now much smaller

Two of the three worries are gone with the row access. What remains is that the code emits markup.

- **SVG is not inert.** `<script>`, `<foreignObject>`, `<image href>` and `<use href>` are live in a
  browser context. WeasyPrint ignores script, but the editor preview renders in the author's own
  session. An element/attribute allowlist still applies, on save and on render — but it now guards a
  **fragment confined to the plot layer**, not a whole document, so the allowlist is short: shapes,
  paths, text, `g`, and their geometry/paint attributes.
- **No external references.** `href` to anything off-box is an outbound request from the render
  worker. Refused, not proxied — the `AUTOMATION_LOOKUP_ENDPOINTS` posture.
- **Jinja** runs in a `SandboxedEnvironment` with no loader, a statement/loop budget and a wall-clock
  deadline (`app/flows/ai.py` sets the pattern). The context is six names, so there is very little to
  reach out of.

### The preview

The editor cannot evaluate Jinja — it is TypeScript against a Python worker — and the chart contract
test exists precisely because **the preview must not lie about the PDF**. So a custom chart's preview
is **server-rendered**, debounced, through the endpoint that already renders server-side. One
implementation, no drift. The chrome is identical on both sides by construction, since neither side
draws it from the author's code.

### Work

| Layer  | Change                                                                                                                |
| ------ | --------------------------------------------------------------------------------------------------------------------- |
| API    | `render/custom_marks.py` — sandboxed Jinja over the projected context, SVG allowlist on the emitted fragment          |
| API    | A validation endpoint; a refusal names the offending element or attribute, never a generic failure                    |
| Render | `charts.py` exposes its scales + plot box, and drops the fragment into the series layer                               |
| DB     | None — it is a `data-comp-*` attribute like every other                                                               |
| Editor | A `custom` chart type; a code pane in the drawer (CodeMirror is already there for the code view); server-side preview |
| Tests  | The allowlist element by element; a sandbox-escape battery; budget and deadline; a refusal that names the node        |

Estimate: **2–3 days.** Down from 4–6 because the data half is gone and the allowlist now covers a
fragment rather than a document.

## 3. Order

Build **1 first**, and not only because it is smaller. Saved components is a large fraction of what
custom code is being asked for: a chunk of "we need more chart shapes" turns out to be "we need the
same chart, configured the way we always configure it, without doing it by hand each time". Ship
presets, watch which shapes are still genuinely missing, and let that decide what custom code has to
support.

They also compose: a custom chart is worth saving as a preset far more than a built-in one is, since
it carries authored code rather than a handful of switches.

## 4. Open questions

- Do presets belong to the **firm** only, or should Graphene ship a starter set the way it does for
  datasets (`0152_dataset_catalogue`)? A platform-provided set answers "what good looks like" on day
  one for a firm with no templates yet.
- Should a preset be able to carry a **dataset binding** after all, for a firm whose charts all read
  the same dataset? Suggest no for v1 — it is addable later, and the reverse is not.
- Custom chart code: is this **firm-authored** or **Graphene-authored on a firm's behalf**? Less
  pivotal than it was — with row access gone the surface is small either way — but it decides whether
  the code pane ships to every firm or sits behind an operations flag, the `flows.ai_tenants`
  posture.
- Is a **gauge or a radar** actually wanted? Neither is marks in an x/y plot, so neither is reachable
  through this hook. If one of them is the real requirement, say so before §2 is built — it is a
  different feature with a different estimate.
