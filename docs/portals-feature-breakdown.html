2 The modular workflow — step catalogue

"Workflows replace onboarding." A workflow is a per-tenant, versioned graph of steps; each step is a pluggable module backed by its own table. Turn steps on/off and reorder per client — no code change.

Guards become data, not code. Today's hard-coded onboarding order (application-state.ts) and the Starlight 7-stage case chain (Adviser prep → Admin sign-off → Paraplanning → Adviser review → Compliance (conditional) → Client meeting → Account opening) both express as a workflow definition. Routing rules (trainee CAS → senior; high-risk product → compliance) are config. Tasks are the primitive that advances it.

3 Feature descriptions

Clean descriptions grounded in the Starlight specs and the code being migrated.

Platform & data

Auth & access (WorkOS) ✔ done 3 Jul

All portals · built

Comprehensive WorkOS: multi-tenant organisations, TOTP MFA, roles + permissions (RBAC + relationship scope, enforced as RLS claims), sealed sessions, JWT-verified API. Client access is admin-provisioned invite + magic-link (no self-signup); joint clients get separate linked logins. An adviser "role profile" makes the adviser view read-mostly; admin stays full access. No enterprise SSO/SAML — WorkOS-managed auth only.

Delivered 1 Jun–16 Jul: auth end-to-end, project-per-tenant WorkOS + environments, self-hosted invites (Resend), per-portal access, granular ops RBAC, unified permission registry, white-label branding + studio. Joint-client linking rides on the CRM.

SEI / Seccl data 1.5 ew

All portals · in progress

Per-tenant DuckDB warehouse + FastAPI data service ingesting clients, accounts, valuations, performance, assets and transactions from the Seccl API and SEI SFTP via provider adapters (registry + seccl/sei) and a pgmq sync queue. Client sees own holdings/performance; adviser sees the book; admin oversees. Analytics / NL→SQL / Atlas are out of scope for the portals/Futura build (a separate data-platform track); the SEI/Seccl integration lays the data foundation only.

Delivered 19–20 Jul: bucket-per-tenant object storage + per-user S3 credentials, per-tenant DuckLake (in-process reads), Seccl interlace sync + webhooks + marts, ML Dynamics book sync, provider enablement + lake fan-out, admin /platforms cockpit. Remaining: SEI ingestion + go-live hardening.

Contacts & CRM 0.5 ew

All portals · built

Contacts, relationships, notes and vulnerability records; the case record is the client hub. Joint clients are linked with a shared-visibility toggle; campaign/referral source is captured at case creation; advisers see their book, admins see all.

Delivered 10–15 Jul: clients list + create, client record (holdings / txns / notes / adviser / login / instructions), client documents view, firm dashboard. Remaining: vulnerability + campaign capture polish; the case-record hub lands with Cases.

Documents 0.5 ew

All portals · built — gen engine landed early

Storage (S3 / RustFS), taxonomy, versioning, RLS visibility. Adviser-issued docs + e-sign (engagement, client agreement, privacy, key facts, fee) with a status lifecycle (Sent → Viewed → Accepted / Outstanding / Returned). Client uploads — the firm classifies, never the client. Template library per trading-style + product, field-mapped and versioned; auto/manual chase; SAR PDF export. The generation engine (Jinja2/WeasyPrint) is phase 2.

Delivered 13–15 Jul: documents schema + endpoints, upload/send/request/archive, viewer + same-origin proxy, client fulfil flow, template editor + versioned schemas, datasets catalogue, async render worker (generation — pulled forward from P2). Remaining: document admin (taxonomy/hard-delete/audit), share links, tags/versions.

Advice engine

Workflow engine 3 ew

Adviser drives · admin configures · client completes · new (designed)

The generic, per-tenant engine: definitions → immutable versioned graph → instances → steps → transitions → triggers. Each step points at its module's table via a generic pointer (no hard FK), so any capability plugs in. Replaces the hard-coded onboarding flow; drives the case chain; triggers advance from the event stream. This is the "flexible per client" backbone.

Reuse: adopt the north-star design (schema.md §8, proposed-schema.sql) — RLS-complete, Postgres-18 validated.

Forms — fact-find · risk · suitability · terms 1.5 ew

PD1 (engine + UI) · all portals · in progress — builder live

One data-driven, versioned questionnaire engine (template → version → instance → submission), ~25 field types, conditional logic, repeating sections, risk scoring → bands and a suitability rules engine, over a per-tenant fields registry for custom fields. Renders "Your Details" (9 sections, shared with the Chester Rose LVP work), the in-house risk profiler, and terms acceptance. Advisers review with soft-facts / rationale / edit-on-behalf; the original client answers are preserved forever.

Reuse: graphene-platform pkgs/questionnaires (scoring + suitability engines, built) + pkgs/fields runtime; consolidate the two field systems into one forms.fields.

Applications 2.5 ew

Adviser / admin · migrate

The application object — applicants (individual/corporate/trust/child), accounts (product + model + risk), and roles — with product types GIA/ISA/JISA/SIPP/bonds/third-party pension. The adviser pipeline, declaration, and the final account-opening gate that hands off to custody sync. The existing status machine's gate logic becomes workflow guards.

Migrate: graphene-platform onboarding.* + application-state.ts gate rules → the workflow engine; rebuild UI in SvelteKit, data behind FastAPI+RLS.

ID / AML 2 ew

PD1 (all) · client capture · adviser review · admin queue · migrate + rebuild

A unified, tenant-scoped case joining identity verification (photo ID + selfie + conditional proof of address) with AML screening (sanctions / PEP / adverse-media) and ongoing monitoring. Providers are swappable per tenant behind adapters — SmartSearch (Futura's choice), CreditSafe, iDenfy — with a normalised decision vocabulary. Adviser gets auto results or a manual-override path (declaration of likeness); admin works an AML queue with a completeness/gap engine. PEP/EDD is phase 2 (binary result first). Kept to ~2 ew because the existing app's client algorithms, data model and state machines port almost directly — the new work is the provider abstraction + RLS multi-tenancy.

Reuse: aml-idv-internal — the 541-line CreditSafe API doc, client algorithms (token cache, backoff, tail-vs-full sync), state machines, completeness engine. Rebuild: multi-tenancy/RLS, the provider abstraction, unified case model, multi-tenant webhooks.

Case ops & collaboration

Cases 2 ew

Adviser / admin · new

A first-class case object created by admin (auto-invites the client, seeds the first task). The case record aggregates the workflow chain, Letters of Authority (received / awaiting + chase / not-required / paper-by-post), tasks, the notes taxonomy, vulnerability, a unified history feed, and meta. Advisers see their pipeline; admins see every case across trading styles. Close-case with a reason.

Source: Starlight adviser + admin specs (the case record is the central screen).

Tasks 2 ew

Admin / adviser / pools · new

The operating primitive that advances the workflow — closing a stage's tasks auto-creates the next stage's. Team-owned (admin / adviser / paraplanning / compliance), pool or personal, with filter / group / bulk (complete, snooze, reassign, chase), default tasks per stage, and due-date / ageing / escalation. The admin task queue is the central work surface.

Source: Starlight — "tasks drive case movement".

Messages 1.5 ew

All portals · new

Two-way secure client↔adviser messaging with inline attachments, unread badges and a dashboard widget. Email alerts carry the subject only — the body stays in the portal. Notes/messages are tagged internal vs client-visible; full threads export to the SAR pack.

Source: Starlight client + adviser specs.

Notifications 1.5 ew

All portals · new

In-portal bell + email across case-state changes, messages, signature requests, ID outcomes, vulnerability changes and document chases. Clients control preferences; admins configure a channel matrix (email / SMS / in-portal), throttling and out-of-hours no-chase windows.

Source: Starlight; wires to the events stream.

SIPP

Morgan Lloyd (SIPP) 7 ew

Adviser UI · client view · admin ops · in progress — Dynamics book sync live 19 Jul

The SIPP integration — transfers, daily valuations, the account-open saga, contributions + HMRC relief-at-source, drawdown, illustration (CTC XML v1.6), and three-way reconciliation — surfaced as the ml_saga workflow step plus adviser UI, client view and admin ops. Portals-specific (Tavistock/CR); not part of Starlight Phase 1. See the timeline view for the sequenced plan.

5 Migration notes

Applications & the advice engine — from graphene-platform

The team already wrote the target design: a generic workflow.* engine, a merged forms.fields registry, and a data-driven questionnaire engine with scoring + suitability. Adopt the design, re-implement for the portals stack (SvelteKit + FastAPI + Postgres RLS) rather than porting the Next.js/Drizzle app or the hard-coded state machine.

  • Reuse: pkgs/questionnaires engines, pkgs/fields runtime, application-state.ts gate rules (as workflow guards), proposed-schema.sql DDL, the services/api custodian-sync adapter pattern.
  • Rebuild: all React step UIs → SvelteKit; Drizzle → FastAPI + RLS tenant_session; hard-coded orchestration → the workflow engine.

ID / AML — from aml-idv-internal

The source is dual-provider (iDenfy IDV + CreditSafe AML) and single-tenant. The portals module is one tenant-scoped case behind swappable provider adapters, so SmartSearch (Futura), CreditSafe and iDenfy coexist per tenant.

  • Reuse: the CreditSafe API doc + client algorithms, the sync/cache & completeness engines, the IDV/AML state machines and data shapes.
  • Rebuild: multi-tenancy + RLS, the ScreeningProvider/IdvProvider abstractions with a normalised decision vocabulary, WorkOS auth, a unified case model, and multi-tenant webhooks + scheduled sync.
