# Partner API

The firm-facing HTTP API is the Litestar package `apps/api/external`, beside the FastAPI portal API in `apps/api/app`. It is its own process (`python -m external`, moon task `api:external-dev`, started by `moon run :dev`). It is not mounted on `app.main`, and `api:dump-openapi` still imports `app.main` only.

Locally it listens on `127.0.0.1:8010` (`EXTERNAL_HOST`, `EXTERNAL_PORT`). `EXTERNAL_STUB` defaults to `true`, so the process serves the in-memory stub and does not open a database. Deployed environments run the same `api` image as a second compose service, `external`, with the command `python -m external`, `EXTERNAL_HOST=0.0.0.0`, and `EXTERNAL_STUB` set to `false` unless that variable is already set. It uses the API's `DATABASE_URL`. `SCREENING_API_KEY` is the screening provider key used when a live check is created; blank means those calls fail closed rather than leaving a check pending. `SCREENING_WEBHOOK_SECRET` verifies the inbound screening webhook; blank refuses it. `SECRETS_MASTER_KEY` is the Fernet key the external process uses to encrypt a firm's webhook signing secret, the same key as the API and the worker; blank fails `PUT /webhook` closed. It also takes the object-storage settings (`S3_*`, the compose `*s3` block), because a firm's uploaded documents are stored there; without them an upload is `503` `storage_unavailable`. Firms call this service on its own domain. The portal API stays on `:8000`.

`/docs` is one Scalar reference (1.71.0). The page loads that script from this process at `/docs/scalar-api-reference.js`. The file is `apps/api/external/static/scalar-api-reference.js`, copied into the API image with the rest of `apps/api`. Overview, Authentication, Versioning, Rate limits, Errors, Webhooks, and Custodian matching are headings in the OpenAPI `info.description`, which Scalar turns into top-level content pages. The Clients and Checks guides are those tags' descriptions, which the classic layout renders above that tag's operations. Generate MCP is off (`mcp.disabled`). Where a caller can receive more than one body, the success response carries a named `examples` map and each example's `summary` is the label.

For firms that integrate directly, the contract replaces the portal's own identity and AML steps. Screening rows live in `compliance.*`. The firm-facing spec, guides, errors, and response bodies do not name the screening provider.

Public ids are the usual 12-character nanoid from `app.ids.new_id`, with no type prefix.

## Versioning

Send `X-Version: v1`. URLs are not versioned. A missing header means the latest version, which is v1, and the response echoes the version that was applied (`x-version: v1`). An unknown value is `400` with code `unknown_version`. That response does not echo the rejected value.

## Clients

`POST /clients` creates a client. `type` defaults to `person`. The request body examples are Minimal Individual (the required person fields only), Individual (optional person fields, `identities`, and a filled address), and Organisation (`type: company`, company fields, and an address).

A person requires `first_name`, `last_name`, `dob`, `email`, `nationality` (at least one ISO alpha-2 code), and `address`. A missing nationality is a validation error on the client.

A company requires `email`, `company.name`, and either `company.incorporation_country` or `address.country`. A company does not require nationality.

Optional person fields: `middle_name`, `gender` (`male` or `female`), `birth_country`, `mobile`, `telephone`, and `identities`. `first_name` and `last_name` allow letters, spaces, hyphens, and apostrophes, the same rule as a portal contact. A date of birth may be today and must not be in the future. `mobile` is stored on `crm.contacts.mobile` and `telephone` on `crm.contacts.phone`. Both use the portal phone check (a UK number, or `+` and an international number).

`identities` is an optional array. Each item has `type` (`national_insurance_number` — a UK National Insurance number, `ssn` — a US Social Security number, `social_insurance_number`, `tax_identification_number`, or `national_identity_number`) and `identifier`. A type may appear once. The first item is written to `crm.contacts.national_identifier`.

Optional company fields: `website`, `registration_number`, `incorporation_country`, `incorporation_type` (a closed enum in the spec).

`address` is one object. `country` (ISO alpha-2) is required. It may also set `property_number`, `building_name`, `line`, `city`, `state`, `postal_code`, and `from_date`.

Also accepted: `tax_residency` (ISO codes), `reference` (the firm's own id), and `metadata` (at most 50 keys, key at most 40 characters, value at most 500). Keys under `graphene` are reserved. The firm's `metadata` stays with us and is never sent to ComplyCube; the ComplyCube client a check creates carries Graphene's own `graphene_*` keys instead, including the client's uid and the firm's `reference` ([aml.md](aml.md) §9).

Unknown fields are rejected. The client schema has no provider ids and no workflow, check-type, or monitoring settings.

`GET /clients/{uid}`, `GET /clients` (the key's tenant, paginated), and `PATCH /clients/{uid}` (same body, every field optional).

Create writes only the contact columns that were supplied, plus `compliance.clients` and one `compliance.addresses` row for the client. The provider's untouched payload, when a webhook later delivers it, is stored in `body` and is never returned.

## API keys

Credentials stay in `auth.api_keys`. The bearer is verified as the SHA-256 hex digest of the secret (`key_hash`). Scopes are `clients:read`, `clients:write`, `checks:read`, `checks:write`, and `links:write`.

Graphene operations issue keys from the admin portal, on a firm's Settings → API page (`apps/admin/src/routes/tenants/[uid]/settings/api`). The API is `app/routers/partner_access.py` under `/admin/tenants/{tenant_uid}`: `GET /api-keys` lists them, `POST /api-keys` (`name`, `scopes`, optional `expires_at`) mints one, and `POST /api-keys/{key_uid}/revoke` sets `revoked_at` (a second revoke keeps the first time). Reads need `tenants:read` and writes `tenants:write`. `external.keys.mint_key` is the one place a key is made: `live_` and 43 URL-safe characters (256 bits). The secret is in the create response only; the row keeps `key_hash` and `key_prefix` (its first 12 characters), and `created_by` / `revoked_by` are the operator. A key is a tenant service key (`user_id` null). The firm API process stops accepting a revoked key once its 60-second cache entry lapses.

Verification uses an in-process LRU keyed by that digest: a hit lives for 60 seconds, a miss for 5 seconds, and the cache holds about 10,000 entries. A revoke in this process drops the entry immediately; other processes learn within the TTL. `last_used_at` is written at most once a minute per key.

The lookup runs as `service_role` before the tenant is known, because the hash is what discovers the tenant. The session does not publish a platform-portal claim. After the key resolves, every write is scoped to that key's `tenant_id`. A disabled firm (`auth.tenants.enabled` false, or the tenant row missing) is `403` with message "This firm's access is suspended.", including a key still inside the 60-second cache. The cached key is not overwritten, so turning the firm back on is visible on the next request.

The stub accepts only the bearer `test_dummy` and sets `X-Graphene-Stub: true`. Any other bearer is `401`. Live keys use the prefix `live_`. Test keys use `test_`.

`GET /health` is liveness. It does not need a key, and a missing or unknown `X-Version` does not refuse it. Compose probes this path.

## Documents and checks

`POST /clients/{uid}/documents` accepts JSON: `type` (`selfie`, `passport`, `drivers_license`, or `identity`), `side` (`front`, the default, or `back`) and `file` (the image as a raw base64 string, with no `data:` URL prefix; OpenAPI `format: byte`). A passport, driving licence, or identity document also takes `issuing_country` (ISO alpha-2). A selfie does not. `back` is accepted for a driving licence or an identity document only; the back is its own document. A missing or invalid `file` is a validation error. A decoded file larger than 50 MB is `422` `file_too_large`. The response is `uid`, `type`, `side`, and `issuing_country`. The image, provider ids, and any hit payload are not returned. The file bytes are not logged.

The file goes to object storage, not the row: `storage.put_document` into the firm's document bucket (`tenant_storage.document_bucket`, else the shared one) at `files/clients/{contact uid}/{document uid}/original.{ext}`, the client's prefix in the documents library's layout. The content type is sniffed from the bytes (`storage.sniff_document_type`; anything that is not an image or a PDF is kept as `application/octet-stream`), and the name is the type, the side and that extension (`drivers_license-back.jpg`), because the firm sends no name. `compliance.documents` holds `object_key`, `side`, and in `body` the name, content type, size and bucket. The row is written before the object, so a failed upload rolls the row back; an object store that is not configured or not answering is `503` `storage_unavailable`. Rows written before this kept base64 in `body.data` and no `object_key`; an identity check still reads those.

`POST /clients/{uid}/checks` takes `{ "kind": "identity" | "aml" }`. There is no success URL, cancel URL, or redirect URL, and a check does not take or create an account.

`kind: identity` runs against documents already stored for that client. It requires a selfie and the front of a passport, driving licence, or identity document; a back alone does not count. If those are missing the response is `422` `documents_required`. The check sends the newest selfie, the newest front, and the newest back of the same type and issuing country when there is one (`external.live.identity_set`). The stub status is `pending`.

`kind: aml` runs from the name, date of birth, address country, and nationality already on the client. A client with no address country is `422` `address_country_required`. The firm does not choose provider check types, workflows, or monitoring. The stub status is `pending`.

A document whose issuing country is outside the client's nationality list comes back `refer`, even when the provider's own outcome was clear. A residential country that differs from nationality or tax residency does not fail the check.

Statuses are `pending`, `clear`, `refer`, and `rejected`. `GET /checks/{uid}` returns one check and is the source of truth. `GET /clients/{uid}/checks` returns `identity` and `aml`, each `{ "status" }` for the latest check of that kind or null when none exists, plus `checks`, every check for the client, newest first.

Each check has `uid`, `kind` (`identity` or `aml`), `status`, `created_at`, and `updated_at`. An identity check also includes `document_uids` and `issuing_country` when that country is known. An AML check also includes the screened `name`, `dob`, and `country`. The response never includes `body` or `result`, a hit list, a match breakdown, or a provider id.

Firms that want a push register `PUT /webhook` (and `GET` / `DELETE`) for `check.updated`, signed with HMAC. The URL must be HTTPS with no user name or password (`WebhookPut` validation, `400` `invalid_body`), and its host must resolve only to public addresses (`422` `invalid_webhook_url`). `app/complycube/webhook_url.py` owns both rules: `check_syntax` refuses another scheme, credentials, `localhost` and `.local` / `.internal` names, and a non-public IP literal; `resolve_public` refuses a host when any address it resolves to is private, loopback, link-local, multicast, reserved, unspecified, shared (100.64/10), or an IPv6 form carrying one of those (IPv4-mapped, 6to4, Teredo, NAT64). Graphene operations can set, replace and remove the same row from the admin (`GET` / `PUT` / `DELETE /admin/tenants/{tenant_uid}/webhook`), with the same rules and a new secret shown once on every set. The URL and signing secret are stored on `compliance.webhooks`, one row per tenant. The secret is Fernet ciphertext (`secret_ct`), the same envelope as the other secrets on this platform. `authenticated` is granted the url columns and not `secret_ct`. `audit.record()` redacts `secret_ct`, so a principal who can read the audit log cannot sign `check.updated`. The plaintext is returned only on PUT. GET returns the URL and does not select the secret. A restart or another replica reads the same row. The GET remains authoritative if a delivery is missed.

Deliveries are the worker's `_firm_webhooks_loop` (`app/complycube/deliveries.py`). `routing.queue_partner_delivery` queues one `compliance.webhook_deliveries` row per firm-visible status change, with the payload `{"event", "uid", "kind", "status"}` in the firm vocabulary. A pass leases up to 20 due rows (`pending`, `next_attempt_at <= now()`) with `FOR UPDATE SKIP LOCKED`, moving `next_attempt_at` two minutes ahead, in one short transaction; sends them all at once outside any transaction; and records each outcome in a second transaction. So a slow endpoint never holds a row lock or a pooled connection, two workers never send one row at once, and a worker that dies mid-send leaves the row due again. Each send decrypts the firm's current secret, re-checks the URL, resolves the host once and connects to that address (`PinnedTransport`: the request URL's host becomes the IP, while `Host` and the TLS `sni_hostname` stay the name, so the certificate is checked for the name and a rebinding answer cannot move the request). The body is the compact JSON, signed `X-Graphene-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">`, with `X-Graphene-Delivery` (the delivery uid) and `Content-Type: application/json`. The whole attempt, DNS included, has 10 seconds; redirects are not followed and the response body is not read. A 2xx is `sent` with `sent_at`. Any other outcome counts an attempt with the reason in `last_error` and waits 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours, then 24 hours; the seventh failure is `failed`. A row whose webhook is gone is `failed` at once with "The firm has no webhook." (deleting the webhook deletes its deliveries, so that is a race). With `SECRETS_MASTER_KEY` unset nothing can be signed: the loop no-ops, says so hourly, and the rows wait. Delivery is at least once and unordered; the GET is the source of truth. In the admin, `GET /admin/tenants/{tenant_uid}/webhook-deliveries` lists the newest 50 (up to 200), and `POST …/webhook-deliveries/{delivery_uid}/resend` puts a `failed` row back to `pending` with `attempts` 0 (`409` for any other status).

The rate limit is 10 requests a second per API key. Over the limit is `429` `rate_limited`. Unknown bearers share a separate window, not the caller address, and are refused before the key is read, so a run of distinct unknown tokens does not open a database lookup for each guess. A key this process has already accepted is not counted in that window, including after the 60-second record cache expires.

## Provider internals

ComplyCube is the provider. There is one Graphene account; isolation is `tenant_id` on `compliance.*`. The firm API never says the provider's name, and the inbound path is `POST /internal/webhooks/screening` (not a path that names the vendor). That route is excluded from the firm OpenAPI document. The `ComplyCube-Signature` header is the hex HMAC-SHA256 of the raw body under the endpoint secret, compared in constant time. It carries no timestamp. A replayed body is harmless: the event id is unique in `compliance.events`, so a replay is never queued twice, and the consumer takes the status from a fresh `get_check`, not from the body. An event with no id is refused with 400.

The provider client's `externalId` is the contact `uid`. A nationality list is stored in full; the provider is sent the first code. An address is sent only once `line`, `city`, and `country` are all present. Before a check starts, the process lists that provider client's addresses and uploads one when none exist, including on a retry that already has the provider client id saved. A country on its own does not upload an address and does not stop an AML check.

Identity does not open a hosted session. The firm's files are read back from object storage (or, for an old row, decoded from `body.data`) and sent on as base64 JSON: the provider client creates a document (`passport`, `driving_license`, or `national_identity_card`), uploads the front image, uploads the back when there is one, uploads the selfie as a live photo, then creates an `identity_check`. In the same transaction as the check row, the provider's document and live photo are written as `compliance.documents` (`provider_document_id`, `classification` `proof_of_identity`) and `compliance.live_photos` (`provider_photo_id`) rows carrying the object keys of the front (`object_key`), the back when one was sent (`back_object_key`, 0224) and the selfie. The event consumer's upserts on those provider ids never write those keys, and these inserts fill them with `COALESCE` when the consumer got there first, and the operations console's identity block reads the images the firm sent from ComplyCube by those provider ids (`GET /aml/checks/{uid}/images/{part}`). Those provider rows are not the firm's documents: every firm read (`SELECT_DOCUMENTS`, and the `documents` of `GET /checks/{uid}` and `GET /clients/{uid}/checks`) skips a row with a `provider_document_id`, so they never appear in `document_uids` and are never submitted as a firm file. AML is a single `extensive_screening_check` that asks for ongoing monitoring, as every Graphene screen does; on a ComplyCube plan without monitoring it runs without it ([aml.md](aml.md) §8).

Subscribed events are `check.pending`, `check.completed`, `check.completed.clear`, `check.completed.attention`, `check.completed.match_confirmed`, `check.completed.rejected`, `check.failed`, `check.updated`, `check.monitoring.attention`, and `client.updated`. The receiver only verifies the signature, inserts the `compliance.events` row and returns 200; it does no provider call. The worker's `_complycube_events_loop` (`app/complycube/consumer.py`) drains the inbox: one transaction under a `pg_try_advisory_xact_lock`, batches of 20, one savepoint per event. Each event fetches the check, the client and any address, document or live photo it points at, records the result (and the AML matches in `compliance.matches`), and routes it only when the stored status really changed (`app/complycube/routing.py`). A provider error (429, 5xx, transport) leaves the event for the next pass without counting a failure; any other error counts one, and an event is parked after 5. `failed` means ComplyCube could not run the check: it is not a result, the firm API reads it as `pending`, and Graphene operations run it again.

## Provider sync storage

Each provider object is stored on its typed table: the columns we query, and `body` jsonb holding the payload untouched. That includes a hit list and any other field the firm API does not return. Metadata stays in `body` only.

`compliance.clients` also stores `entity_name`, `email`, `mobile`, `telephone`, `external_id` (indexed where it is set), `joined_date`, `client_type`, and the person fields `first_name`, `middle_name`, `last_name`, `dob`, `gender`, `nationality`, `birth_country`, `ssn`, `social_insurance_number`, `national_identity_number`, and `tax_identification_number`, plus the company fields `company_name`, `website`, `registration_number`, `incorporation_country`, and `incorporation_type`. `compliance.addresses` adds `address_type`, `property_number`, `building_name`, and `to_date`. `compliance.documents` adds `document_type`, `document_number`, and `issuing_state`, and `side` (0222: `front` or `back`, null for a front written before it). `compliance.live_photos` adds `perform_liveness_check`, `content_type`, `size_bytes`, and `download_link`. `compliance.checks` adds `provider_type`, `provider_status`, `outcome`, `entity_name`, `enable_monitoring`, `client_consent`, `provider_document_id`, `provider_address_id`, `provider_live_photo_id`, and `provider_live_video_id`. `status` and `kind` stay our public values. When the provider sends a `result` object it is stored in `result`; otherwise `result` stays the status and outcome summary. `body` is the full object either way. These columns are not in the firm OpenAPI document, the guides, the errors, or the response bodies. A client or check that arrives before it matches a `crm.contacts` row is still stored. `tenant_id` and `contact_id` are null, the full payload is kept, and the inbox row is marked processed so it leaves the oldest-20 claim. Unmatched rows are not dropped. RLS hides them from firm API callers (`tenant_id IS NOT NULL` and the firm's own `WHERE tenant_id`). `service_role` can match them later. The firm API stays the short view: responses, OpenAPI, guides, and errors do not include `body`, `result`, a hit list, or the provider's name. The inbound body is refused above 256 KiB before the signature is checked, the same cap as the other unauthenticated callbacks.

A live `POST /clients/{uid}/checks` calls the screening provider: identity uploads the stored document and selfie and starts an identity check; AML starts a screening check. The stub does not call the provider and stays `pending`. The firm response still starts as `pending` and never names the provider. The inbound event is what moves the status.

Outcomes map to `pending`, `clear`, `refer`, and `rejected`. `attention` and a conflicting issuing country are `refer`. Operations resolves `refer`. The portal then reads `compliance.checks`. `crm.kyc_checks` stays the summary the flow engine and the client record read.

## Queue fallback

pgmq is Decision 5 in `docs/data-architecture.md` and is not enabled by a migration yet. `enqueue` checks `pg_extension` for `pgmq` and, when the row is there, calls `pgmq.send` on `compliance_sync`. When the extension is absent it returns false. The inbox row is the durable record either way, so a consumer can `SELECT … FROM compliance.events WHERE processed_at IS NULL … FOR UPDATE SKIP LOCKED`.

## Tipping-off

Every `compliance.*` row is tenant-scoped when it has a tenant. RLS is enabled and forced. Staff read through `auth.tenant_lineage()`. The policies do not use `auth.contact_scope()`: a person must not be able to select their own screening row. A client session has an empty lineage, so the read returns nothing. `compliance.events` has no `updated_at` and no `set_updated_at` trigger. Unmatched clients, checks, and events (`tenant_id` null) stay invisible to firms until a tenant is attached. They remain in the table.

## Custodians

`PUT /clients/{uid}/custodians` takes `{ "provider": "seccl" | "sei", "external_id" }` and upserts `platform.links` for the contact (the table introduced as `platform.platform_links` in 0003 and renamed in 0043). The link type is `primary`. A check does not create an account.
