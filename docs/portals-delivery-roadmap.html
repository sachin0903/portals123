4 Feature descriptions

Clean descriptions grounded in the Starlight specs and the code being migrated. Delivered/remaining re-checked against the repository on 2 Aug — where a card says something is not built, that is a direct check of the code, not an inference from the board.

Platform & data

Auth & access (WorkOS) ✔ done 3 Jul

All portals · built

Comprehensive WorkOS: multi-tenant organisations, TOTP MFA, roles + permissions (RBAC + relationship scope, enforced as RLS claims), sealed sessions, JWT-verified API. Client access is admin-provisioned invite + magic-link (no self-signup); joint clients get separate linked logins. No enterprise SSO/SAML — WorkOS-managed auth only.

Delivered 1 Jun–16 Jul: auth end-to-end, project-per-tenant WorkOS + environments, self-hosted invites (Resend), per-portal access, granular ops RBAC, unified permission registry, white-label branding + studio. Since: the login rate limiter wired up and API observability exposed (28 Jul); RLS tightened materially by migrations 0030–0035 — proven against the testcontainer chain but not yet applied to any live database.

SEI / Seccl data 1 ew

All portals · built — conform outstanding

Per-tenant DuckLake warehouse + in-process lake reads ingesting clients, accounts, valuations, performance, assets and transactions from the Seccl API and SEI SFTP via provider adapters. Client sees own holdings/performance; adviser sees the book; admin oversees. Analytics / NL→SQL / Atlas stay out of scope for this build.

Delivered 19–20 Jul: bucket-per-tenant object storage + per-user S3 credentials (TECH-86), per-tenant DuckLake, Seccl sync + webhooks + marts (TECH-87), ML Dynamics book sync, provider enablement + lake fan-out, admin /platforms cockpit. Delivered 27 Jul–2 Aug: the SEI custodian (SFTP + PGP + byte-exact archive + trailer verification + a typed 47-model raw layer + the entity layer), marts renamed to one platform.* consumption schema, one conformed cross-provider shape (org_key/org_path replacing three tenancy dialects), canonical entities 0041 + app/materialise.py, and Seccl proven staging-API → canonical OLTP. Remaining: conform SEI + ML to the same shape, port Sachin's mart SQL (cherry-picked, not importable, outside the gates), go-live hardening.

Contacts & CRM 0.5 ew

All portals · built

Contacts, relationships, notes and vulnerability records; the case record is the client hub. Joint clients are linked with a shared-visibility toggle; campaign/referral source captured at case creation; advisers see their book, admins see all.

Delivered 10–15 Jul: clients list + create, client record, client documents view, firm dashboard. Since: the book surfaces moved onto the shared DataTable, /accounts + account detail added (holdings moved off the client page to the account that holds them), per-client activity search, dashboard-first UX. The 30 Jul re-audit deleted the rescaled performance series and rescaled holdings units rather than papering over them — every figure now carries a source and an as-at. Remaining: vulnerability + campaign polish; nothing settles an instruction; the case-record hub lands with Cases (TECH-77).

Delivered 13–15 Jul: schema + endpoints, upload/send/request/archive, viewer + same-origin proxy, client fulfil flow, template editor + versioned schemas, datasets catalogue, async render worker (generation, TECH-81). Advice engine

Workflow engine 0.5 ew

Adviser drives · admin configures · client completes · built 24 Jul

The generic, per-tenant engine: definitions → immutable versioned graph → instances → steps → transitions → triggers. Each step points at its module's table via a generic pointer, so any capability plugs in. Replaces the hard-coded onboarding flow; drives the case chain. The "flexible per client" backbone — and the gate for Futura (TECH-63).

Delivered 23–24 Jul as flows v2 (0021–0025, ~30 commits, Gio): the versioned graph, planner + DB orchestrator, module step-handlers with CRM write-back, the transactional outbox + dispatcher, and a Svelte-Flow visual builder with condition/repeat nodes and AND/OR visibility groups. The legacy onboarding flow was ported onto it and the v1 flat-case engine deleted. Remaining: admin config UI polish. Jira: TECH-73 still reads To Do / Sachin / 3 Sep — five weeks and one owner out of date; §6 no longer treats it as a risk.

Forms — fact-find · risk · suitability · terms 1 ew

PD1 (engine + UI) · all portals · in progress — past due

One data-driven, versioned questionnaire engine (template → version → instance → submission), ~25 field types, conditional logic, repeating sections, risk scoring → bands and a suitability rules engine, over a per-tenant fields registry. Renders "Your Details", the in-house risk profiler, and terms acceptance; original client answers preserved forever.

Built: the builder, persistence (0011_forms), the /forms API, client fill, and flow-configured intake authored on the Start node (24 Jul). Not built — checked directly: there is no scoring config, no risk band and no suitability rules engine anywhere in the forms code. Jira: TECH-74 passed its 31 Jul date; it is the only advice-engine story that slipped, and Futura's TECH-61/62 depend on it.

ID / AML 0.5 ew

PD1 (all) · AML built 29 Jul · IDV manual

A unified, tenant-scoped case joining identity verification (photo ID + selfie + conditional PoA) with AML screening and ongoing monitoring. Providers swappable per tenant — SmartSearch (Futura), CreditSafe, iDenfy — with a normalised decision vocabulary. PEP/EDD is phase 2. Kept to ~2 ew because the existing app's algorithms, data model and state machines port almost directly.

Delivered 29 Jul (0037/0038): the Creditsafe mirror, the ops-owned console, the tipping-off control (POCA 2002 s.333A — the read policy omits contact_scope, guarded behaviourally, by a pg_policies assertion and by a static client-portal test), operator-attributable writes with no service-account fallback, ops-only adjudication that is structural rather than a check, unattributed-profile linking, and the aml_check flow trigger. Verified against the live sandbox. Not built: any IDV provider — iDenfy was dropped, so verify_identity is a manual gate; no monitoring-alert ingestion; no per-tenant entitlement or spend cap.
