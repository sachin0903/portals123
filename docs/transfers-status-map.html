Transfer status model & reconciliation

One canonical lifecycle, three custodian vocabularies. This maps Morgan Lloyd, SEI and Seccl transfer statuses onto Graphene's transfer_status saga, then traces how a transfer reconciles all the way down to a single platform.transactions row — and what it would take to run the same workbench across all three systems.

05

One workbench, three systems

Today the workbench and backend assume one route: external SIPP → Morgan Lloyd → SEI. Going generic means modelling other routes — including transfers that live entirely inside Seccl or inside SEI — behind a route-agnostic transfer abstraction.

live External SIPP→Morgan Lloyd→SEI Cross-system pension transfer. Three-way reconciliation. The current saga.
next Seccl a/c→Seccl a/c Intra-Seccl (Internal stock transfer / inter-account cash). Single ledger, no cross-provider recon — the simplest route and best first generalisation.
next SEI a/c→SEI a/c Intra-SEI free movement (transferIn/Out → settlePendedItem). Settles within SEI custody.
later External→Seccl  /  cross-custody Other ceding→receiving combinations once the abstraction is proven.
WorkstreamEffortWhere it lands
Canonical transfer modelGeneralise ML-specific pensions.transfers → route descriptor (source/destination system, intra vs cross), provider-agnostic status, links to expectation + asset legs. Medium backend · schema (expand/contract migration)
Status normalisation layerTurn §02–03 crosswalk into code: each provider adapter maps raw status → canonical, + reverse for display. Pinned by per-provider enum tests. Small–Med backend · correctness-critical
Per-route orchestrationThe crux. Today: one hardcoded ML→SEI saga. Generic needs a saga per route (intra-Seccl: Pending→Placed→Completed; intra-SEI: initiate→settle→confirm), each with its own idempotency keys & reconciliation source. Large backend · state machines + runners
Provider adapter / API coverageSame shape as the workbench's ops registry, server-side: create / poll / update / settle / cancel / status per provider. Scope to the UK transfer subset. Medium backend · per provider
Reconciliation generalisationEach route declares its recon source(s) and 2-way vs 3-way compare. The expectation↔transaction bridge already generalises (all sources normalise into platform.transactions). Medium backend · mostly in place
UI generalisationRoute-aware flow ribbon (per-route stage models), route/type selector in the composer, fewer custody legs for intra-system. Ops registry, status buckets, reconciliation panel & rail already generalise. Small–Med frontend · ~70% reusable
Bottom line. The workbench is already ~70% generic — the provider-grouped ops registry, canonical status buckets and per-row stage rail are the right abstractions. The real cost is backend: a route-agnostic transfer model and a saga per route. Scope "all endpoints" to the UK transfer subset (SEI free movements + cash receipts + custody edits + pending status; Seccl product/stock transfers + book cost; ML transfer ops) — SEI's US recurring / withholding / disbursement surface balloons effort for little value here. Start with intra-Seccl (simplest lifecycle) to prove the abstraction.
